# Приёмная ДАО Русь: анкета Mini App и управляемое приглашение

- **Статус:** принято к реализации; этап 1 реализован (схема, API и Reception Mini App auth), остальные этапы ожидают реализации
- **Дата:** 2026-10-10
- **Область:** DAO Core, Telegram-бот Приёмной, Telegram-форум, Хранитель

## Цель и границы

Убрать ручной перенос данных новичка из переписки в профиль Core, не автоматизируя решение о приглашении. Сохранить действующую текстовую переписку, возможность прямого вступления в форум и принцип: подача заявки **не означает членства** в ДАО.

## Пользовательский сценарий

1. Бот «Приёмная ДАО Русь» при /start предлагает кнопку **«Заполнить анкету»**, открывающую Telegram Mini App на домене Core.
2. Новичок заполняет **город** и **род занятий** (обязательные свободные текстовые поля), **возраст** (необязательное целое число).
3. Перед отправкой показывает предпросмотр сведений, которые появятся в теме «Приёмная»; публикация возраста — только по отдельному явному согласию.
4. Кнопка **«Отправить заявку»** сохраняет заявку в Core. Подтверждение различает «сохранена» и «доставлена в Приёмную».
5. Core публикует заявку **в существующей теме «Приёмная» Telegram-форума**, без создания отдельного чата, через бот Приёмной.
6. Участники и Хранитель знакомятся с человеком через существующий relay «форум ↔ личные сообщения».
7. **Только Хранитель или явно уполномоченный им участник** нажимает кнопку **«Пригласить»** в административном журнале заявки. Бот Приёмной отправляет ссылку в личный чат. Успешный ответ Telegram отмечает лишь *отправку*, но не прочтение и не вступление.
8. Факт вступления устанавливается независимо по Telegram membership. Данные анкеты связываются с существующим/созданным профилем Core по проверенному Telegram ID, без дублей и без перезаписи самостоятельно изменённых полей.
9. Вступление напрямую в форум, без анкеты, продолжает работать; такой участник может дополнить профиль позднее.

## Компоненты и потоки

- **Telegram Reception bot**: кнопка запуска Mini App, существующая переписка, отправка приглашения после команды Хранителя.
- **Mini App в Core**: экран анкеты, валидация, предпросмотр, понятный статус подачи; без стороннего конструктора.
- **API Core**: проверяет Telegram `initData` **токеном Reception bot**, а не Dev bot; Telegram ID берётся только из проверенного `initData`, не из пользовательского поля.
- **PostgreSQL**: новая сущность `reception_applications`, состояние заявки и отдельный учёт исходящих действий/доставки. Связь с `participants` и `external_identities` по Telegram ID после разрешения существующей идентичности.
- **Публикация**: отдельная от существующей `reception_relay_updates` операция, с собственным стабильным ID заявки и записью Telegram message ID при подтверждённой доставке.
- **Админ Core → Люди → Заявки**: содержимое, состояния, дата подачи, ссылка на пост в Telegram, кнопка «Пригласить», диагностические действия.
- **Фоновая доставка**: переиспользовать существующий worker, если это не смешивает учёт уведомлений и заявок. Новый сервис без необходимости не создавать.

## Модель состояний

Не сводить три независимых измерения к одному статусу.

| Измерение | Состояния / признаки |
| --- | --- |
| Заявка | подана; отложена; приглашение подтверждено как отправленное; закрыта; вступление учитывается отдельно |
| Публикация заявки | ожидает; доставлена (Telegram message ID); требует проверки |
| Приглашение | не запрошено; ожидает отправки; отправлено (Telegram подтвердил); ошибка; требует проверки |
| Членство | вне форума; в форуме (источник — Telegram membership) |

Статусы можно уточнить при реализации, но независимость измерений обязательна. Не объявлять сообщение доставленным при одном только сохранении заявки.

## Доставка и сбои

- Сначала атомарно записать заявку и задачу публикации в Core, затем обращаться к Telegram.
- Отправлять без параллельной гонки по одной заявке, блокировать двойное нажатие и повторную обработку одной операции.
- **Подтверждённая недоставка** допускает безопасную автоматическую повторную попытку после устранения причины; учитывать `retry_after` при Telegram 429.
- **Таймаут, сетевой обрыв, неизвестный итог запроса** дают статус «требует проверки». Не повторять вслепую: Telegram Bot API не гарантирует идемпотентность `sendMessage`.
- Хранитель может сопоставить сообщение в форуме, указать факт доставки либо вручную разрешить повтор. Для пригласительной ссылки применяется такое же правило: исключать дубли и преждевременное приглашение.
- Не хранить токены в журнале и не логировать чувствительные данные сверх необходимого.
- Если Telegram недоступен, кандидат видит «Заявка сохранена, доставка ожидается», а журнал сохраняет обращение.

## Согласование с текущим Core

- Существующий `/api/auth/telegram/mini-app` проверяет `initData` токеном Dev bot и создаёт/находит Participant; для заявки Reception bot **нужен отдельный поток аутентификации**, не создающий участника только из-за анкеты.
- `checkForumAndInvite` уже способен при определённых настройках отправлять приглашение при /start или login. В новой ветке заявок этот автоматизм **не должен обходить решение Хранителя**. Проверить существующие конфигурации/сценарии и обеспечить единое правило выдачи приглашений для заявителей; прямой вход и добровольность участия в форуме сохранить.
- `reception_relay_updates` обслуживает обычную переписку. Не смешивать её с журналом заявок и исходящей публикацией.
- В случае уже существующего Participant разрешать идентичность по Telegram ID; сохранять правки пользователя в профиле и не создавать дубли.

## Безопасность и приватность

- Проверка подписи и срока действия `initData` на сервере, авторизация Хранителя на каждом административном действии.
- Валидация длины, типа и пределов полей; безопасное форматирование текста Telegram и защита от злоупотребления частыми заявками.
- Перед отправкой явно указывать, что город и занятия публикуются в теме форума; возраст публиковать **только с отдельного согласия**. Определить доступ к возрасту в Core и возможность исправить/удалить персональные данные.
- Не считать наличие анкеты подтверждением соблюдения Кодекса или основанием для присвоения membership_status.

## Порядок внедрения

Контракт реализованного этапа 1 и инварианты хранения:

3. Публикация в тему с учётом доставки, журнал Хранителя.

6. Сквозные тесты: успешный путь, повторные запросы, обрыв Telegram, неопределённая доставка, действующий Participant, отказ от публикации возраста, двусторонний relay.
7. Код и миграции → тесты/typecheck/build → commit/push в `main`; production deploy **после отдельной проверки** и подтверждения готовности Telegram-настроек.

## Критерии приёмки

- Один ввод трёх полей → одна сохранённая заявка → одна подтверждённая публикация в теме «Приёмная».
- При сбое Telegram данные сохраняются, статус честно отражает неопределённость, нет автоматических дублей.
- Ссылка уходит **только после действия уполномоченного Хранителя**, не по самой подаче анкеты.
- Вступивший получает сведения в профиле без ручного переноса и без дублирования личности.
- Старый relay, прямое вступление, Dev bot и существующие профили продолжают работать.

## Не входит в эту задачу

Оценка убеждений заявителя ИИ, автоматическое одобрение членства, новая система репутации, новые форумы/каналы, расширенная анкета или создание самостоятельной инфраструктуры при уже существующих подходящих компонентах.

# Telegram-агенты DAO Rus

- **Статус:** архитектурная спецификация / рабочая гипотеза
- **Дата:** 1 октября 2026 года
- **Связанный документ:** [Telegram-first архитектура](./telegram-first.md)

Этот документ уточняет роли Telegram-ботов DAO Rus и описывает первый вертикальный срез Хранителя участника. Он не заменяет общую Telegram-first архитектуру и не означает, что все перечисленные механизмы уже реализованы.

## 1. Принцип

Telegram остаётся живой социальной средой, а DAO Core — источником устойчивого состояния, идентичности, истории и институциональных фактов.

Telegram-боты не должны создавать параллельные сущности пользователей, отдельную репутацию или собственную модель членства. Они являются агентными интерфейсами к Core.

```text
Telegram
    ├── Приёмная ДАО Русь
    └── DAO RUS Dev bot
              ↓
      Telegram integration layer
              ↓
           DAO Core
              ↓
        PostgreSQL / events
```

Оба бота используют одну связь `telegram_user_id ↔ core_user_id` и общие сервисы Core.

## 2. Роли

### 2.1. DAO Core

DAO Core является источником истины для:

- Participant / идентичности;
- профиля;
- Human Verification и графа подтверждений;
- Membership;
- потребностей, возможностей и ресурсов;
- истории значимых событий;
- состояния онбординга и других долговременных фактов.

На текущем Telegram-first этапе подтверждённое вступление в основной Telegram-форум является достаточным событием для автоматического создания Participant в Core и привязки его Telegram identity. Это не означает автоматической Human Verification, принятия Кодекса, заполнения профиля, начисления репутации или иных статусов: эти состояния остаются независимыми.

### 2.2. «Приёмная ДАО Русь»

Публичная роль — вход и ориентация.

Внутренняя агентная роль — **Хранитель жизненного цикла участника**.

Задачи:

- встречать новых людей;
- объяснять устройство ДАО и основные точки входа;
- выявлять незавершённый онбординг;
- мягко достраивать пропущенные социальные связи;
- замечать выпадение участника из основных контуров;
- при явном уходе запрашивать добровольный exit-feedback;
- в перспективе поддерживать добровольный win-back.

Хранитель не оценивает человека и не является надзорным агентом. Его задача — находить места, где ДАО не смогло нормально встретить, связать, поддержать или удержать участника.

### 2.3. DAO RUS Dev bot

Операционный интерфейс к функциям Core.

Базовые направления:

- «Мне нужно»;
- «Могу помочь»;
- мои запросы и отклики;
- поиск людей и ресурсов;
- персональные уведомления;
- быстрые действия над сущностями Core.

Dev bot не должен дублировать полноценный онбординг «Приёмной». Если он обнаруживает незавершённый социальный маршрут, он может направить пользователя в «Приёмную».

## 3. Низкий порог входа

Прохождение «Приёмной» не является обязательным предварительным условием доступа к Core.

Базовый продуктовый принцип:

> **Низкий порог входа, постепенный рост доверия, Кодекс в центре.**

Допустимы как минимум два маршрута:

```text
прямая ссылка → Core → осмотрелся → заполнил профиль → нашёл интерес /
потребность → вступил в полезное взаимодействие → возникли связи и верификация
```

и:

```text
Приёмная → разговор / объяснение → понимание устройства → Core
```

Хранитель нужен именно для того, чтобы эти маршруты не конкурировали, а сходились: если человек пришёл напрямую, система мягко помогает ему достроить социальную часть пути.


### 3.1. Telegram-форум как вход в Core

Пока DAO Rus организационно базируется в Telegram, Core не является вторым контуром вступления или более высокой ступенью участия. Для пользователя Core — структурированное расширение той же среды.

Поэтому подтверждённое событие вступления в основной Telegram-форум должно автоматически:

1. найти Participant по Telegram identity;
2. если Participant отсутствует — создать минимальный Participant;
3. связать с ним Telegram identity;
4. зафиксировать `forum_joined` / соответствующее событие членства в форуме.

При первом последующем входе в Core человек должен попадать в уже существующий профиль, а не проходить повторную регистрацию.

Автоматическое создание Participant означает только присутствие человека в организационном контуре ДАО. Оно само по себе не означает Human Verification, принятия Кодекса, заполнения профиля, репутации или предоставления специальных прав.

Простая видимость аккаунта ботом, личное сообщение в «Приёмную» или иное техническое наблюдение не являются достаточным основанием для автоматического создания Participant. Основанием является именно подтверждённое вступление в основной Telegram-форум.

Для участников, состоявших в форуме до запуска этой механики, допустима постепенная синхронизация при последующем подтверждённом контакте с Core, поскольку Bot API не предоставляет полный ретроспективный roster участников.


## 4. Приватность до добровольного раскрытия

«Приёмная» является посредником между внешним человеком и внутренней средой ДАО. Сам факт обращения человека к Telegram-боту «Приёмная ДАО Русь» не означает согласия на раскрытие его Telegram-личности участникам форума.

Базовый принцип:

> **Идентичность раскрывается по мере необходимости и по воле самого человека, а не взыскивается на входе.**

Из этого следуют требования:

- Core может знать техническую связь между Telegram-пользователем и диалогом, необходимую для маршрутизации сообщений;
- эта техническая идентичность не должна автоматически раскрываться участникам форума;
- по умолчанию собеседник может отображаться под нейтральным стабильным псевдонимом вроде `Гость #N`;
- Telegram display name, username и другие идентифицирующие данные раскрываются внутренней стороне только после явного действия или согласия самого пользователя;
- отсутствие публичного username не мешает полноценному двустороннему диалогу;
- numeric Telegram user id не отображается участникам форума;
- маршрутизация ответов работает через внутренний mapping Core и не зависит от публичного раскрытия личности;
- приватность не должна разрушать непрерывность разговора: один и тот же собеседник в рамках диалога остаётся узнаваемым под стабильным псевдонимом;
- содержание сообщений не следует сохранять только ради этой механики.

Продуктовый смысл этого принципа расширяет идею низкого порога входа: человек может сначала вступить в разговор с ДАО, не раскрывая себя внутреннему сообществу, а затем добровольно перейти от псевдонимного контакта к представлению и участию.

Принцип был выявлен при первом реальном production-контакте после перехода «Приёмной» с внешнего relay на Core. Relay через `copyMessage` доставил сообщение в форум без имени отправителя. Это рассматривается не только как UX-дефект, но и как обнаруженное полезное свойство: посредник способен обеспечить двусторонний контакт, не раскрывая автоматически личность внешнего собеседника. При дальнейшей реализации это свойство следует сохранить и сделать сознательным.

## 5. Событийная модель

Хранитель должен по возможности реагировать на значимые события, а не постоянно сканировать поведение всех участников.

Концептуальный поток:

```text
UserRegistered
    ↓
TelegramLinked
    ↓
OnboardingIncomplete
    ↓
ForumJoined
    ↓
ProfileCompleted
    ↓
FirstInteraction
    ↓
NeedCreated / OfferCreated
    ↓
ResponseReceived
    ↓
InactivePeriodStarted
    ↓
ForumLeft
    ↓
ExitFeedbackReceived
    ↓
Rejoined
```

Названия событий пока являются архитектурными обозначениями, а не утверждённым API.

Каждое событие должно быть связано с исходным фактом и Participant, если Participant уже существует. Реакция агента на событие должна быть отделена от самого события: один и тот же факт в будущем смогут использовать Web UI, Mini App, аналитика или другие агенты.

## 6. Состояние онбординга

Онбординг не следует сводить к одному бинарному полю `onboarding_complete`.

Система должна уметь определять отдельные факты, например:

```text
core_registered
telegram_linked
forum_joined
profile_started
profile_completed
code_seen
first_interaction
```

Конкретная схема хранения определяется при реализации. Важно сохранить возможность различать незавершённые шаги и не превращать их автоматически в условия допуска.

## 7. Первый vertical slice

Первый MVP Хранителя должен проверять один реальный сценарий:

> **Пользователь зарегистрировался в Core по прямой ссылке, но не состоит в основном Telegram-форуме ДАО.**

Поток:

```text
1. Core знает Participant и связанный Telegram user id.
2. Integration layer проверяет членство этого Telegram user id в основном форуме.
3. Если членства нет, Core фиксирует состояние / событие OnboardingIncomplete.
4. «Приёмная ДАО Русь» отправляет одно мягкое персональное приглашение.
5. Пользователь вступает в форум.
6. Изменение членства фиксируется.
7. Повторные приглашения прекращаются.
```

Сообщение должно объяснять пользу форума, а не создавать впечатление обязательной проверки или нарушения правил.

Членство в форуме не является обязательным условием доступа к Core.

## 8. Ограничения первого среза

В первый vertical slice не входят:

- ИИ-интервьюер;
- анализ психопрофиля;
- контроль неактивности;
- exit interview;
- win-back;
- персональная лента всех событий;
- автоматическая оценка качества участия;
- сложная оркестрация нескольких агентов.

Цель первого среза — доказать сквозную цепочку:

```text
Core state
→ значимое событие
→ Telegram-агент
→ полезное мягкое действие
→ изменение состояния Core
```

После live-проверки этого контура можно расширять Хранителя на сценарий «новичок застрял», затем на уход и exit-feedback.

## 9. Принципы реализации

1. **Один источник истины.** Боты не ведут самостоятельную базу участников.
2. **Событие отдельно от реакции.** Core фиксирует факт; агент решает, как на него отреагировать.
3. **Мягкий онбординг.** Незавершённый шаг — повод помочь, а не основание ограничивать доступ.
4. **Минимизация данных.** Хранитель использует только данные, необходимые для конкретного сценария.
5. **Отсутствие скрытого social score.** Неактивность, выход или незавершённый онбординг не превращаются в оценку человека.
6. **Проверяемость.** Значимые изменения состояния должны быть прослеживаемы до события и действия.
7. **Эволюционность.** Сначала один работающий vertical slice, затем расширение по реальным наблюдениям.

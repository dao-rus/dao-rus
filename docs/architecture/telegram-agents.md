# Telegram-агенты DAO Rus

- **Статус:** архитектурная спецификация / рабочая гипотеза
- **Дата:** 4 октября 2026 года
- **Связанный документ:** [Telegram-first архитектура](./telegram-first.md)

Этот документ уточняет роли Telegram-ботов DAO Rus и описывает первый вертикальный срез Хранителя участника. Он не заменяет общую Telegram-first архитектуру и не означает, что все перечисленные механизмы уже реализованы.

## 1. Принцип

Telegram остаётся живой социальной средой, а DAO Core — источником устойчивого состояния, идентичности, истории и институциональных фактов.

Telegram-боты не должны создавать параллельные сущности пользователей, отдельную репутацию или собственную модель членства. Они являются агентными интерфейсами к Core.

```text
Telegram
    ├── Приёмная ДАО Русь
    └── DAO RUS Dev bot
              ↓
      Telegram integration layer
              ↓
           DAO Core
              ↓
        PostgreSQL / events
```

Оба бота используют одну связь `telegram_user_id ↔ core_user_id` и общие сервисы Core.

## 2. Роли

### 2.1. DAO Core

DAO Core является источником истины для:

- Participant / идентичности;
- профиля;
- Human Verification и графа подтверждений;
- Membership;
- потребностей, возможностей и ресурсов;
- истории значимых событий;
- состояния онбординга и других долговременных фактов.

На текущем Telegram-first этапе подтверждённое вступление в основной Telegram-форум является достаточным событием для автоматического создания Participant в Core и привязки его Telegram identity. Это не означает автоматической Human Verification, принятия Кодекса, заполнения профиля, начисления репутации или иных статусов: эти состояния остаются независимыми.

### 2.2. «Приёмная ДАО Русь»

Публичная роль — вход и ориентация.

Внутренняя агентная роль — **Хранитель жизненного цикла участника**.

Задачи:

- встречать новых людей;
- объяснять устройство ДАО и основные точки входа;
- выявлять незавершённый онбординг;
- мягко достраивать пропущенные социальные связи;
- замечать выпадение участника из основных контуров;
- при явном уходе запрашивать добровольный exit-feedback;
- в перспективе поддерживать добровольный win-back.

Хранитель не оценивает человека и не является надзорным агентом. Его задача — находить места, где ДАО не смогло нормально встретить, связать, поддержать или удержать участника.

### 2.3. DAO RUS Dev bot

Операционный интерфейс к функциям Core.

Базовые направления:

- «Мне нужно»;
- «Могу помочь»;
- мои запросы и отклики;
- поиск людей и ресурсов;
- персональные уведомления;
- быстрые действия над сущностями Core.

Dev bot не должен дублировать полноценный онбординг «Приёмной». Если он обнаруживает незавершённый социальный маршрут, он может направить пользователя в «Приёмную».

## 3. Низкий порог входа

Прохождение «Приёмной» не является обязательным предварительным условием доступа к Core.

Базовый продуктовый принцип:

> **Низкий порог входа, постепенный рост доверия, Кодекс в центре.**

Допустимы как минимум два маршрута:

```text
прямая ссылка → Core → осмотрелся → заполнил профиль → нашёл интерес /
потребность → вступил в полезное взаимодействие → возникли связи и верификация
```

и:

```text
Приёмная → разговор / объяснение → понимание устройства → Core
```

Хранитель нужен именно для того, чтобы эти маршруты не конкурировали, а сходились: если человек пришёл напрямую, система мягко помогает ему достроить социальную часть пути.


### 3.1. Telegram-форум как вход в Core

Пока DAO Rus организационно базируется в Telegram, Core не является вторым контуром вступления или более высокой ступенью участия. Для пользователя Core — структурированное расширение той же среды.

Поэтому подтверждённое событие вступления в основной Telegram-форум должно автоматически:

1. найти Participant по Telegram identity;
2. если Participant отсутствует — создать минимальный Participant;
3. связать с ним Telegram identity;
4. зафиксировать `forum_joined` / соответствующее событие членства в форуме.

При первом последующем входе в Core человек должен попадать в уже существующий профиль, а не проходить повторную регистрацию.

Автоматическое создание Participant означает только присутствие человека в организационном контуре ДАО. Оно само по себе не означает Human Verification, принятия Кодекса, заполнения профиля, репутации или предоставления специальных прав.

Простая видимость аккаунта ботом, личное сообщение в «Приёмную» или иное техническое наблюдение не являются достаточным основанием для автоматического создания Participant. Основанием является именно подтверждённое вступление в основной Telegram-форум.

Для участников, состоявших в форуме до запуска этой механики, допустима постепенная синхронизация при последующем подтверждённом контакте с Core, поскольку Bot API не предоставляет полный ретроспективный roster участников.


## 4. Атрибуция сообщений в Приёмной

На текущем этапе перед скопированным личным сообщением бот показывает внутренней
стороне Telegram display name отправителя (`first_name` и, если есть,
`last_name`) и `@username`, если он есть. Отсутствие username не мешает диалогу.
Прежняя политика анонимного отображения или псевдонима по умолчанию больше не
действует.

Numeric Telegram user ID не показывается участникам форума. Core хранит только
необходимые идентификаторы для маршрутизации ответа через mapping скопированного
сообщения; содержание переписки ради атрибуции не сохраняется. Ответ оператора
на скопированное сообщение по-прежнему направляется в личный чат отправителя.

## 5. Событийная модель

Хранитель должен по возможности реагировать на значимые события, а не постоянно сканировать поведение всех участников.

Концептуальный поток:

```text
UserRegistered
    ↓
TelegramLinked
    ↓
OnboardingIncomplete
    ↓
ForumJoined
    ↓
ProfileCompleted
    ↓
FirstInteraction
    ↓
NeedCreated / OfferCreated
    ↓
ResponseReceived
    ↓
InactivePeriodStarted
    ↓
ForumLeft
    ↓
ExitFeedbackReceived
    ↓
Rejoined
```

Названия событий пока являются архитектурными обозначениями, а не утверждённым API.

Каждое событие должно быть связано с исходным фактом и Participant, если Participant уже существует. Реакция агента на событие должна быть отделена от самого события: один и тот же факт в будущем смогут использовать Web UI, Mini App, аналитика или другие агенты.

### 5.1. История жизненного цикла форума

Подтверждённые переходы `chat_member` основного форума записываются в Core events:

- первое известное вступление — `forum.joined`;
- возвращение после ранее известного присутствия — `forum.rejoined`;
- присутствовал → Telegram `left` — `forum.left`;
- присутствовал → Telegram `kicked` — `forum.removed`.

Для определения возвращения учитываются существующие события вступления, включая
исторические `onboarding.forum_joined`, и явные события убытия. Одно первоначальное
наблюдение отсутствия не доказывает, что человек уже состоял в форуме.
`forum.removed` фиксирует техническое удаление/бан Telegram и не означает
`membership.excluded`: институциональное исключение требует решения Вече.
Канонический membership status эти события не меняют.

Participant хранится в поле события; payload содержит только `source`, `observed_at`
и `telegram_update_id`, когда он доступен. Повторный update не дублирует историю.
Запоздавший подтверждённый переход сохраняется в истории, но не перезаписывает
более свежее состояние onboarding. Старые события не удаляются при возвращении.
Проверка `getChatMember`, сведённая к присутствию/отсутствию, сохраняет наблюдение
onboarding и не изобретает причину убытия. Старые `onboarding.forum_incomplete`
не преобразуются автоматически: они не различают добровольный выход и удаление.

Read-only раздел «Убытие» в `/admin/guardian` показывает число событий за 30 дней,
общее число и ссылку «История убытия». Полная хронология вынесена в
`/admin/guardian/departures`: от новых событий к старым, включая вернувшихся
участников, ссылки на профили и доступное историческое имя/username из provenance.
Считаются события, а не уникальные люди. Время отображается по Москве.
Отправка exit-feedback не реализована.

## 6. Состояние онбординга

Онбординг не следует сводить к одному бинарному полю `onboarding_complete`.

Система должна уметь определять отдельные факты, например:

```text
core_registered
telegram_linked
forum_joined
profile_started
profile_completed
code_seen
first_interaction
```

Конкретная схема хранения определяется при реализации. Важно сохранить возможность различать незавершённые шаги и не превращать их автоматически в условия допуска.


### 6.1. Первое полезное действие → DARUS

После вступления человек обычно субъективно считает задачу присоединения завершённой. Поэтому Core не должен рассчитывать только на добровольное заполнение дополнительных данных и освоение функций.

Базовый поведенческий принцип:

> **Первое полезное действие каждого типа должно по возможности получать немедленную обратную связь и вознаграждение DARUS.**

Примеры таких первых действий: первое заполнение полезного блока профиля, первое «Мне нужно», первое «У меня есть», первое подтверждение знакомого и другие действия, которые увеличивают полезность сети.

Цель награды — сформировать и закрепить связь:

```text
полезное действие
→ система его замечает
→ участник сразу получает DARUS и понятный результат
→ повышается вероятность следующего полезного действия
```

Для защиты от заполнения мусором ради награды **бонус за освоение конкретного действия начисляется только один раз — за первое действие данного типа**. Повторение того же действия само по себе не создаёт новый onboarding-бонус.

Это правило относится именно к стимулированию освоения среды. Оно не запрещает отдельные награды за реально подтверждённый вклад, помощь, исполнение обязательств или иной результат: такие начисления относятся уже к Contribution / дарономике и должны иметь собственное основание.

DARUS в этом контуре является сигналом признанного полезного действия, а не платой за количество кликов или записей.


### 6.2. Onboarding Quests

Невыполненные шаги освоения Core следует показывать участнику как добровольные игровые задания с заранее известной наградой DARUS.

Примеры:

- `Укажите город — так вас смогут находить участники поблизости. +0,1 DARUS`;
- `Заполните «Мне нужно» — сеть сможет искать для вас совпадения. +0,2 DARUS`;
- `Заполните «У меня есть» — сеть сможет находить тех, кому это пригодится. +0,2 DARUS`;
- `Добавьте интересы — это поможет находить людей с близкими интересами. +0,1 DARUS`;
- `Подтвердите знакомого участника — это укрепляет web of trust. +0,3 DARUS`.

Правила UX:

- показываются только ещё не выполненные задания;
- задание не блокирует доступ к функциям Core;
- невыполнение не влечёт штрафа и не уменьшает DARUS;
- за первое выполнение каждого типа задания награда начисляется один раз;
- после выполнения задание исчезает из списка активных или явно отмечается как выполненное;
- в карточке задания объясняется не только размер награды, но и практическая польза действия для участника или сети;
- приоритет отдается простым и понятным первым шагам, чтобы участник быстро получил опыт `действие → результат → вознаграждение`.

Эта механика не превращает Core во второй контур вступления. Участник уже находится в ДАО; задания помогают ему постепенно освоить возможности сети и обогатить данные, необходимые для matching, доверия и кооперации.

## 7. Первый vertical slice

Первый MVP Хранителя должен проверять один реальный сценарий:

> **Пользователь зарегистрировался в Core по прямой ссылке, но не состоит в основном Telegram-форуме ДАО.**

Поток:

```text
1. Core знает Participant и связанный Telegram user id.
2. Integration layer проверяет членство этого Telegram user id в основном форуме.
3. Если членства нет, Core фиксирует состояние / событие OnboardingIncomplete.
4. «Приёмная ДАО Русь» отправляет одно мягкое персональное приглашение.
5. Пользователь вступает в форум.
6. Изменение членства фиксируется.
7. Повторные приглашения прекращаются.
```

Сообщение должно объяснять пользу форума, а не создавать впечатление обязательной проверки или нарушения правил.

Членство в форуме не является обязательным условием доступа к Core.

## 8. Ограничения первого среза

В первый vertical slice не входят:

- ИИ-интервьюер;
- анализ психопрофиля;
- контроль неактивности;
- exit interview;
- win-back;
- персональная лента всех событий;
- автоматическая оценка качества участия;
- сложная оркестрация нескольких агентов.

Цель первого среза — доказать сквозную цепочку:

```text
Core state
→ значимое событие
→ Telegram-агент
→ полезное мягкое действие
→ изменение состояния Core
```

После live-проверки этого контура можно расширять Хранителя на сценарий «новичок застрял», затем на уход и exit-feedback.

## 9. Принципы реализации

1. **Один источник истины.** Боты не ведут самостоятельную базу участников.
2. **Событие отдельно от реакции.** Core фиксирует факт; агент решает, как на него отреагировать.
3. **Мягкий онбординг.** Незавершённый шаг — повод помочь, а не основание ограничивать доступ.
4. **Минимизация данных.** Хранитель использует только данные, необходимые для конкретного сценария.
5. **Отсутствие скрытого social score.** Неактивность, выход или незавершённый онбординг не превращаются в оценку человека.
6. **Проверяемость.** Значимые изменения состояния должны быть прослеживаемы до события и действия.
7. **Эволюционность.** Сначала один работающий vertical slice, затем расширение по реальным наблюдениям.


## 10. Уведомления Core и доставка в Telegram

### 10.1. Канонический объект — Notification в Core

Персональное сообщение участнику должно существовать в DAO Core независимо от внешнего канала доставки.

Базовая схема:

```text
источник сигнала
      ↓
Notification в Core
      ├── visible_in_inbox → /notifications в Ядре
      ↓
Telegram delivery
      ↓
DAO RUS Dev bot
      ↓
sent / blocked / failed / unknown
```

Внутреннее уведомление не является fallback после неудачи Telegram. Оно является каноническим сообщением участнику. Telegram — дополнительный оперативный канал доставки того же сообщения.

Из этого следуют правила:

- создание Notification считается успешным независимо от результата Telegram;
- недоступность Telegram не приводит к потере сообщения;
- участник видит в Core уведомления с `visible_in_inbox = true`;
- факт прочтения в Core хранится отдельно от факта технической доставки в Telegram;
- успешный ответ Bot API подтверждает принятие сообщения Telegram, но не его прочтение участником.

### 10.2. Источники уведомлений

Разные причины создания сообщения не должны создавать отдельные механизмы доставки.

На первом этапе предусматриваются два источника:

1. **Системный сигнал Хранителя.** Например, у актуального участника не указан город или отсутствуют интересы, из-за чего снижается полезность функций ДАО для него.
2. **Административный технический сигнал.** Например, сообщение об онлайн-встрече, адресованное выбранной аудитории по городу и/или интересам.

В дальнейшем тем же контуром могут пользоваться matching, Вече, проекты и другие подсистемы.

Концептуально:

```text
Хранитель ───────────────┐
                         │
Администратор ───────────┼─→ Notification ─→ Core UI
                         │          │
Matching / Вече / ... ───┘          └─→ Telegram delivery
```

Источник определяет причину и аудиторию. Доставка не должна содержать бизнес-логику источника.

### 10.3. Минимальная модель данных

Следующий этап реализации должен ввести как минимум две сущности.

`notifications`:

- получатель `participant_id`;
- тип уведомления;
- текст;
- необязательная ссылка действия;
- источник (`system` / `admin` и далее при необходимости);
- создавший администратор, если применимо;
- время создания;
- время прочтения в Core.
- `visible_in_inbox boolean NOT NULL DEFAULT true`: видимость в Личке Ядра,
  отдельно от хранения канонической записи для аудита и Telegram-доставки.

`notification_deliveries`:

- ссылка на Notification;
- канал доставки, на первом этапе `telegram`;
- состояние `pending / processing / sent / blocked / failed / unknown`;
- время попытки;
- внешний идентификатор сообщения при успешной отправке;
- безопасный код / описание ошибки без секретов.

Отдельная запись доставки в Core не требуется. Список Лички, счётчик непрочитанных
и отметка прочтения учитывают только `visible_in_inbox`. Старые уведомления и
четыре smart/simple сценария остаются видимыми по умолчанию.

### Ручное техническое сообщение

Форма аудитории в `/admin/guardian` использует существующие фильтры: точный город,
OR между интересами, AND между городом и интересами. Администратор задаёт текст
и каналы «Ядро»/«Telegram». Технических параметров Notification и CTA в форме нет.

Повторяемый `technical_broadcast` сохраняет неизменяемый snapshot в
`guardian_campaigns`: автора, текст, фильтры, каналы и итоговые количества.
Сервер заново определяет актуальную аудиторию внутри одной транзакции, создаёт
по одной Notification на получателя и только допустимые pending Telegram deliveries.
Ключ отправки, привязанный к администратору, защищает повтор POST от дублей;
изменённое содержимое с тем же ключом отклоняется. Новое сообщение имеет новый ключ.

«Ядро» создаёт видимую запись без Telegram delivery; «Telegram» — скрытую
каноническую запись и delivery при допустимой identity; оба канала — одну видимую
запись и delivery. Отсутствующая, некорректная или конфликтующая identity пропускает
только Telegram-доставку. HTTP-запрос не вызывает Bot API.

Перед первым включением production worker код и миграции разворачиваются с
`TELEGRAM_NOTIFICATIONS_ENABLED=false`. Затем read-only проверяется вся pending
очередь: получатель, текст, источник/тип, время и campaign. При неожиданных записях
флаг остаётся false. Только известные контролируемые тесты либо пустая очередь
позволяют включить флаг и пересоздать worker штатным compose. Проверка не создаёт
рассылку; существующие тестовые записи должны завершиться, sent — иметь message id,
processing — не зависать. Неопределённые доставки автоматически не повторяются.

### 10.4. Telegram-транспорт

Для персональных операционных уведомлений используется **DAO RUS Dev bot**. «Приёмная ДАО Русь» остаётся отдельным каналом входа, ориентации и relay и не должна использоваться как общий транспорт системных уведомлений.

Production-тест подтвердил возможность `sendMessage` через Dev bot по Telegram user ID, связанному с Participant, на двух тестовых аккаунтах. Это доказывает работоспособность сквозного транспорта, но не означает, что личная доставка гарантированно доступна каждому Participant.

Поэтому доступность Telegram должна устанавливаться по фактическому результату доставки, а не выводиться только из наличия Telegram ID или факта входа через Telegram OIDC.

При неоднозначном сетевом результате доставка получает состояние `unknown`; автоматический немедленный повтор недопустим, чтобы не создавать дубликаты.

Worker атомарно захватывает одну `pending` delivery и фиксирует `processing`
до обращения к Bot API. Он не держит транзакцию БД во время HTTP-запроса.
Если `processing` остаётся без подтверждённого результата более 10 минут,
она переходит в `unknown` без повторной отправки. Автоматического перехода
`unknown` обратно в `pending` нет. Отправка выключена по умолчанию флагом
`TELEGRAM_NOTIFICATIONS_ENABLED=false`.

### 10.5. Кампании Хранителя

Массовое или сегментированное действие строится поверх персональных Notification, а не как отдельная система рассылки.

Для типовых сценариев Хранителя применяется принцип **smart/simple**: администратор формулирует только содержание сообщения, а аудитория, тип действия, подпись CTA, маршрут и правила дедупликации определяются самим сценарием Core. Пользовательский интерфейс не должен требовать знания внутренних URL или технических полей Notification.

Каталог ограничен четырьмя сценариями. Во всех сценариях «актуальный участник» означает
`forum_status='joined'` или `participant.logged_in`, за исключением `left`, `excluded` и roster-ботов.

| Сценарий | Аудитория | Действие | Повтор |
| --- | --- | --- | --- |
| `profile_residence_prompt` | без указанного города | «Указать город», `/profile#residence-name` | один раз для `v1` |
| `profile_interests_prompt` | без интересов любой visibility | «Добавить интересы», `/profile#profile-interests` | один раз для `v1` |
| `town_meeting` | точное выбранное местожительство из Core | без CTA | новая кампания при каждом запуске |
| `online_meeting` | все актуальные участники | без CTA | новая кампания при каждом запуске |

Администратор редактирует только текст; для городской встречи он также выбирает город из
существующих данных Core. Сценарий определяет notification type, правило аудитории,
действие и политику повтора. Предпросмотр не создаёт записей. Финальный POST заново
вычисляет аудиторию в транзакции и сохраняет персональные Notification и допустимые
`pending` delivery. Ключи двух профильных кампаний постоянны (`:v1`), а каждая встреча
получает новый уникальный ключ. Уникальность `(campaign_id, participant_id)` не допускает
двух Notification одному участнику в рамках одного запуска.

В immutable snapshot кампании сохраняются и текст, и системно выбранные параметры действия, чтобы история отражала фактически отправленное сообщение. Но `action_label` и `action_url` не должны приходить из административной формы, если однозначно следуют из типа кампании.

При смене сценария форма сбрасывает текст, выбранный город, предпросмотр и ошибку.
Для профильных сценариев Core читает текущую действующую версию `reward_rules`
для `residence_first_filled` / `interest_first_added`. При активном правиле
предпросмотр показывает отдельную системную заметку о размере DARUS. При запуске
правило читается повторно внутри транзакции; условное предложение «Если вы … впервые»
добавляется к тексту и сохраняется в snapshot кампании и Notification. Администратор
редактирует только исходный человеческий текст. Отсутствующее или неактивное правило
не создаёт обещания награды; встречи не имеют награды. Текущее отсутствие данных
профиля не означает право на повторную историческую награду первого действия.


Концептуальная модель:

```text
Guardian campaign
      ↓ 1:N
Notification
      ↓ 1:N
Delivery
```

Первая практическая кампания:

> **Предложить заполнить интересы всем актуальным участникам, у которых сейчас нет ни одного интереса.**

На первом этапе запуск выполняет администратор вручную из `/admin/guardian`. В дальнейшем тот же сценарий должен запускаться автоматически по правилу Хранителя, не меняя нижележащую инфраструктуру Notification/Delivery.

В v0.2c первый ручной запуск имеет постоянный ключ `profile_interests_prompt:v1`. Администратор редактирует только текст: подпись действия «Добавить интересы», ссылка `/profile#profile-interests` и тип Notification заданы сценарием в коде. Неизменяемый snapshot хранит текст, действие, правило аудитории, администратора и числа созданных Notification и поставленных в очередь Telegram delivery. Предпросмотр не записывает данные; при подтверждении условие отсутствия интересов любой visibility проверяется заново в транзакции. Повторный запуск того же ключа возвращает сохранённый snapshot без новых Notification. Telegram отправляет существующий worker, когда доставка разрешена конфигурацией.

Для кампании обязательны:

- предварительный просмотр аудитории и текста;
- повторная проверка условия перед созданием Notification;
- дедупликация, чтобы повторный запуск или двойной клик не создавал одинаковые сообщения одному участнику;
- неизменяемая история уже запущенной кампании;
- итоговая статистика доставки: создано / sent / blocked / failed / unknown.

Отправка сотен сообщений не должна выполняться внутри одного HTTP-запроса. Для массовой Telegram-доставки нужен фоновый worker, который забирает `pending` deliveries небольшими пачками и фиксирует результат каждой попытки.

### 10.6. Порядок ближайшей реализации

Следующие вертикальные срезы:

1. **v0.2a — Core Notification.** Ввести `notifications` и `notification_deliveries`, страницу `/notifications`, чтение собственных уведомлений и отметку прочтения. Создание Notification не зависит от Telegram.
2. **v0.2b — Telegram delivery worker.** Фоновая доставка `pending` через DAO RUS Dev bot с фиксацией `sent / blocked / failed / unknown`.
3. **v0.2c — Guardian campaign.** Кнопка «Предложить заполнить интересы» в `/admin/guardian`: предпросмотр и подтверждённый однократный запуск на всей подходящей аудитории. Тестовый запуск на выбранных участниках в этот срез не входит.
4. **v0.3 — автоматический Хранитель.** Ручной источник запуска заменяется правилом: если участник достаточно давно находится в ДАО и нужные данные всё ещё отсутствуют, система создаёт то же персональное уведомление автоматически.

Таким образом автоматизируется только источник сигнала; каноническое Notification, внутреннее сообщение, Telegram delivery, дедупликация и история остаются общими.

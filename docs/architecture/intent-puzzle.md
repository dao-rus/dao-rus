# Intent и сборка пазла — рабочая гипотеза

- **Статус:** концептуальная заметка / точка возврата
- **Дата фиксации:** 2026-09-19
- **Связанный документ:** [Философия DAO Rus](../philosophy/philosophy-of-dao-rus.md)
- **Назначение:** сохранить найденный механизм, прежде чем переходить к проектированию реализации

## 1. Основной двигатель: «Я хочу / мне нужно»

Рабочая гипотеза: главным динамическим объектом DAO Rus является не членство,
публикация или голосование, а выраженная воля субъекта:

```text
Я хочу X
Мне нужно X
```

В философском слое это воля. В информационном слое ей соответствует компактный
объект `Intent`.

Важно различать содержание намерения и его технический идентификатор. `Intent`
может иметь ключ, ID, hash/signature и иное компактное машинное представление,
но один hash не содержит семантики, необходимой для поиска совместимых фрагментов.
Конкретная схема данных пока не определена.

## 2. Intent как первый фрагмент пазла

После публикации в разрешённом субъектом пространстве коммуникаций `Intent`
становится фрагментом пазла.

Система не обязана искать один готовый «ответ». Она может искать множество
комплементарных фрагментов:

```text
Intent
  +
Capability
  +
Resource
  +
другой Intent
  +
Relationship
  +
условия
  =
частичное или полное решение
```

Пример:

```text
«Нужно перевезти диван завтра из A в B»
+
«У меня есть пикап»
+
«Я завтра свободен»
+
«Могу помочь с погрузкой»
=
почти или полностью собранный пазл
```

## 3. Не бинарное совпадение, а степень достаточности

Композиция может удовлетворять намерение частично:

```text
35%
67%
92%
100%
```

Эти числа пока являются метафорой, а не спецификацией универсального рейтинга.

Принцип важнее конкретной математики: агент должен уметь различать:

- готовое решение;
- близкое решение;
- частичную конфигурацию;
- отсутствующий фрагмент.

Оценка достаточности предпочтительно принадлежит субъекту или его агенту, а не
центральному алгоритму, который объявляет единственную «правильную» меру
совпадения.

## 4. Дефицит становится поисковым объектом

Если пазл собран не полностью, важнейшим результатом matching становится не
просто «ничего не найдено», а описание **недостающего фрагмента**.

```text
Intent
→ внутренний matching
→ частичная сборка
→ обнаружение дефицита
→ поиск недостающего фрагмента
```

Именно дефицит может запускать распространение запроса за пределы существующей
сети.

## 5. Вирусность «на плечах потребности»

Если внутри сети нет нужного фрагмента, участник может знать человека вне DAO,
который им обладает.

```text
запрос
→ внутри сети решения нет
→ найден недостающий Capability / Resource
→ участник знает подходящего outsider
→ «Передать запрос»
→ обычное человеческое сообщение
→ outsider видит конкретную потребность
→ помогает решить её
→ возникает новая связь
```

Принцип:

**DAO приглашает человека не «в платформу», а в недостающую клетку конкретного
пазла.**

Поэтому приглашение несёт немедленную полезность и контекст. Человеку не нужно
сначала принять идентичность сообщества, зарегистрироваться ради регистрации и
только потом искать смысл участия.

Сначала возникает задача и полезное взаимодействие. Принадлежность и идентичность
могут возникнуть позже как результат повторяющейся кооперации.

## 6. Дефицит связности производит новую связность

Неудачный внутренний поиск не обязательно является ошибкой системы. Он может
быть механизмом роста.

```text
не хватает возможности X
→ сеть ищет X вовне
→ появляется человек / ресурс / компетенция X
→ текущий Intent решён
→ X остаётся доступным для будущих комбинаций
```

Таким образом, сеть потенциально растёт не случайным набором участников, а в
направлении реально обнаруживаемых дефицитов.

Каждый успешный внешний поиск одновременно:

1. помогает закрыть текущий Intent;
2. увеличивает пространство будущих решений.

Это кандидат на основной вирусный цикл DAO Rus.

## 7. Пользователь становится брокером связности

Цикл не заканчивается тем, что newcomer получил или оказал услугу.

Рабочая цепочка:

```text
OUTSIDER
→ INTRODUCTION
→ FAVOR / SERVICE
→ RECIPROCITY
→ RELATIONSHIP
→ BROKER
```

После положительного опыта человек может сам получить чужой запрос и передать его
следующему подходящему человеку.

Полный цикл:

```text
Intent
→ дефицит
→ внешний поиск
→ новый субъект
→ решение
→ новая связь
→ новый Intent
→ новый внешний поиск
```

Сеть воспроизводит себя через полезные отношения.

## 8. Сообщество как результат, а не условие

Предпочтительная последовательность:

```text
потребность
→ помощь
→ доверие
→ повторение
→ связь
→ сообщество
→ идентичность
```

а не:

```text
идентичность
→ членство
→ сообщество
→ активность
→ возможная польза
```

«Русь» в этой модели может пониматься как возникающая культура и структура
отношений, если взаимодействия систематически воспроизводят базовые принципы
DAO Rus.

## 9. Из множества Intent возникает общее

Тот же механизм масштабируется от частной задачи к общему делу.

Например:

```text
«Хочу детскую площадку во дворе»
+
37 близких Intent
=
потенциальный Common
```

Далее пазл может собираться из людей, компетенций, ресурсов, денег, разрешений и
готовности действовать.

Когда множество индивидуальных воль обнаруживает общий предмет, появляется
основание для совместной процедуры решения:

```text
Intent₁ + Intent₂ + ... + Intentₙ
→ Common
→ обсуждение / согласование
→ Veche / Decision
→ Agreement
→ Action
```

Отсюда рабочая гипотеза: **народовластие является одним из частных случаев
сборки комплементарных человеческих воль вокруг общего предмета**, а не отдельным
модулем голосований, пристроенным к системе сверху.

## 10. Кандидат на фундаментальный алгоритм DAO Rus

На текущем этапе главный алгоритмический объект проекта можно сформулировать так:

> Децентрализованная сборка комплементарных Intent, Capability, Resource и
> Relationship в конфигурации, достаточные для добровольно согласованного
> действия.

Короткая цепочка:

```text
Я хочу
→ Intent
→ Matching
→ Puzzle
→ Deficit
→ Search
→ Relationship
→ Agreement
→ Action
```

Если возникает общий предмет:

```text
множество Intent
→ Common
→ Veche
→ коллективное Agreement
→ Action
```

## 11. Что пока НЕ зафиксировано

Эта заметка намеренно не определяет:

- формат `Intent`;
- способ семантического matching;
- алгоритм вычисления степени достаточности;
- маршрутизацию запросов между узлами;
- модель приватности и раскрытия Intent;
- защиту от спама, Sybil-атак и злоупотреблений;
- устройство локальных AI-агентов;
- сетевой транспорт;
- экономическую модель;
- конкретную реализацию DAO Core.

Это следующие задачи проектирования. Их нельзя преждевременно принимать за
решённые только потому, что концептуальная модель выглядит связной.

## 12. Точка возврата

При возобновлении работы начать с вопроса:

**Что является минимальным `Intent` в протоколе и какая минимальная информация
необходима агенту, чтобы обнаружить комплементарность, не раскрывая лишнего?**

После этого отдельно проектировать:

```text
Intent schema
→ Matching
→ Sufficiency / Deficit
→ Routing
→ External handoff
→ Agreement
→ Action / verification
```


## 13. «Оставленная дверь»: латентный узел сети

Внешний запрос должен не только передавать конкретный `Intent`, но и оставлять
получателю минимальную дверь обратно в DAO Rus.

Пример сообщения:

```text
Привет, это Алексей. Тут человеку нужен X. Можешь помочь?

Это запрос через DAO Rus.
Если тебе когда-нибудь что-нибудь понадобится — просто нажми «Мне нужно».
```

Получателю не обязательно сначала становиться «участником», создавать полный
профиль или разбираться в устройстве системы. Он может ответить на конкретный
запрос как внешний человек.

После контакта у него должна остаться максимально простая точка возврата:

```text
[ МНЕ НУЖНО ]
```

Техническая форма пока не определяется: сохранённая ссылка, ярлык/PWA, mini app
или иной механизм. Существенно сохранение доступной точки входа в протокол.

```text
получил чужой Intent
→ помог / отказался / отложил
→ сохранил дверь
→ прошло время
→ возникла собственная потребность
→ «Мне нужно»
→ собственный Intent
→ сеть начинает собирать новый пазл
```

Такой человек может рассматриваться как **латентный узел**: связь с протоколом уже
существует, но активируется его собственной волей и потребностью.

Это создаёт отложенную вирусность:

```text
немедленный эффект:
outsider помогает закрыть текущий пазл

отложенный эффект:
у outsider остаётся дверь в сеть
→ будущая потребность активирует новый Intent
```

Поэтому распространение DAO Rus потенциально определяется не только числом
немедленно активировавшихся людей, но и количеством оставленных доступных дверей,
которые могут активироваться позднее.

Продуктовый принцип:

**не требовать вступления — оставить возможность попросить.**

Минимальный интерфейс первого контакта должен стремиться не к регистрации, а к
двум действиям:

```text
ответить на конкретный запрос
или
сохранить [МНЕ НУЖНО] на будущее
```

Полная идентичность, ключи, профиль и иные элементы могут создаваться лениво —
только тогда, когда они действительно необходимы для конкретного действия.


## 14. Периферия и ядро: разные степени включённости

Вирусный вход «на плечах потребности» предполагает, что сеть не делится только
на участников и неучастников. Возникают разные степени включённости.

Условно можно различать:

```text
латентный контакт
→ периферийный участник
→ всё более верифицированный участник
→ ядро
```

Это пока не формальные статусы протокола, а модель для дальнейшего
проектирования.

**Периферия** — люди, которые вошли через конкретную потребность или запрос,
пользуются частью возможностей DAO Rus, но ещё слабо связаны с сетью и
недостаточно подтверждены другими субъектами.

**Ядро** — область сети с высокой плотностью устойчивых связей, взаимных
подтверждений и истории действий. Ядро не должно назначаться сверху как
административная элита.

Ядерные участники естественным образом могут становиться примером и ориентиром
для периферии: их положение объясняется наблюдаемой историей отношений,
подтверждений, выполненных обязательств и вклада, а не формальным званием.

## 15. Права должны зависеть от основания, а не от сословия

Права периферийных участников могут быть уже прав ядра там, где действие требует
более сильной верификации или доверия.

Причина ограничения:

```text
не «ты участник второго сорта»,
а «для этого действия пока недостаточно подтверждений»
```

Например, создать `Intent` и попросить о помощи может быть возможно почти с
первого контакта, тогда как доступ к общему ресурсу или иное чувствительное
действие может требовать большей подтверждённости.

Следует избегать превращения этой модели в единую лестницу власти. Как минимум
нужно различать независимые измерения:

```text
включённость
верификация / доверие
репутация в конкретном контексте
права в конкретном общем
экономический баланс DARUS
```

Они могут коррелировать, но не должны автоматически сводиться к одному рангу.

## 16. DARUS: экономический слой не должен автоматически становиться властью

Рабочая гипотеза: у участников ядра баланс DARUS в среднем может быть выше,
поскольку они чаще действуют в сети, создают ценность и участвуют в обмене.
Однако сам по себе баланс DARUS не должен автоматически:

- повышать верификацию;
- давать больше доверия;
- давать больше голоса в вече;
- давать право распоряжаться общим;
- переводить человека в ядро.

Иначе экономический капитал превращается в универсальный политический и
репутационный ранг.

Предварительное разделение:

```text
верификация → основание для доверительных прав
договор / вече → права относительно общего
DARUS → экономические возможности
```

## 17. DARUS и дефицитный ресурс внимания

Премиальные функции могут оплачиваться DARUS, если покупается не власть над
другими субъектами, а дополнительный сервис или ограниченный ресурс сети.

Один из кандидатов — повышенное распространение `Intent`:

```text
обычный Intent
→ органическое распространение по релевантным связям

премиальный Intent
→ DARUS
→ дополнительная видимость / расширенный радиус / размещение в общем потоке
```

Возможный частный случай — объявление на первой странице DAO или массовое
уведомление по разрешённому каналу.

Но оплата не должна превращаться в право захватить чужое внимание. Получатель
должен сохранять контроль над тем, какие категории массовых или премиальных
уведомлений он разрешает.

Принцип:

**можно купить дополнительную возможность предложить; нельзя купить обязанность
другого человека увидеть, принять или исполнить предложение.**

Таким образом, экономический механизм остаётся совместимым со свободой субъекта.

## 13. Проверяемый срез Blind Match / Relay v0.1

Витрина `/exchange` показывает активные `profile_signals` четырёх видов:
`need`, `can`, `want`, `have`. Записи `public` и `members` доступны участникам
с именем автора; `network_blind` для `need` и `have` остаётся публикацией без
identity автора. Чужой профиль анонимную запись не показывает, и счётчики
сигналов в списке участников её не учитывают. Режим `match_only` остаётся
непубликуемым исходным сигналом для будущего matching.

Каждый отклик создаёт отдельный `relay_encounters` и приватную переписку
`relay_messages`. Core допускает к ним только автора сигнала и откликнувшегося.
До взаимного согласия обеих сторон сервер не возвращает identity другой
стороны. Первый consent фиксирует только волю согласившегося; после второго
состояние становится `revealed`, и участникам открываются имя и ссылка на
профиль друг друга. Отмена переводит диалог в архив, запрещает новые сообщения
и не возвращает контактные данные в архивном представлении. Это правило
сохраняется независимо от Web UI, Mini App или другого адаптера.

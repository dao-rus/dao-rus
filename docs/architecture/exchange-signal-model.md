# Модель Signals: переход A1

Смысл Exchange определяет [exchange-human-connectivity.md](exchange-human-connectivity.md).
Этот документ описывает только хранение и совместимость перехода A1.

## Каталог типов

`signal_types(key, display_name, enabled)` — каталог типов существующего
`profile_signals`, а не отдельная система Signals. `key` — стабильный машинный
ключ (строчная латиница, цифры и `_`, до 64 символов). `display_name` — данные;
бизнес-правила не зависят от названия. Использованный ключ защищён внешним ключом.

Начальный набор: `need`, `search`, `can`, `have`, `want`, `know`, `skill`, `doing`,
`idea`, `dating`. Новый тип добавляется записью каталога, без расширения SQL CHECK
или TypeScript union. Административного интерфейса на A1 нет.

Отключённый тип запрещает создание новых Signals. Уже существующие записи
сохраняются и могут читаться и архивироваться по прежним правилам. Изменение типа
записи также требует разрешённого типа. Проверка каталога блокирует строку `FOR SHARE`
до конца транзакции создания; такую же проверку выполняет DB-триггер для SQL-писателей.

## Содержание и совместимость

Канонические поля `profile_signals`:

- `label` — обязательное ядро, 1–120 символов, непустое после `btrim`;
- `description` — опциональный контекст, до 10000 символов; отсутствие — `NULL`;
- `legacy_body` — признак дословного содержания из прежнего ввода одним `body`.

`body` остаётся совместимым представлением для профиля, Exchange, сообществ и
Relay. Для структурированной записи это `label` и, при наличии описания,
два перевода строки + `description`. BEFORE-триггер синхронизирует представление,
а CHECK проверяет равенство; расходящиеся версии содержания не допускаются.
Изменять `body` структурированной записи напрямую запрещено. Изменения
`label/description` автоматически обновляют `body`.

`createProfileSignalWithDatabase` / `createProfileSignal` — доменный путь создания
структурированных записей любого включённого типа. Возвращает UUID и, если
положено, результат прежней onboarding-награды. Каталог читается через
`listSignalTypesWithDatabase` / `listSignalTypes`.

`addProfileSignalWithDatabase` / `addProfileSignal` сохраняют контракт старого
редактора и `/need`: тип, `body` до 500 символов, видимость, результат награды.
Этот адаптер поддерживает только прежние четыре типа. Триггер принимает такие
body-only INSERT и UPDATE старых записей и дословно переносит их в `label` с
`description=NULL` и `legacy_body=true`. Новые категории должны использовать
структурированный путь. Текущий UI не расширяется.

## Перенос старых записей

Миграция `032_exchange_signal_types.sql` копирует старый `body` **целиком** в
`label`, оставляет `description=NULL` и отмечает `legacy_body=true`. UUID,
авторы, видимость, состояния, timestamps и ссылки `relay_encounters` сохраняются.
Перенос охватывает также закрытые и архивные записи.

Принципиальное ограничение: у старого свободного текста нельзя автоматически
получить краткое семантическое ядро без интерпретации или потери содержания.
Поэтому старые labels являются временными дословными формулировками и могут
превышать 120 символов. Даже исторические пустые/длинные строки, разрешённые
прежней SQL-схемой, сохраняются. Исключение применяется только к записям с
`legacy_body=true`; новые body-only записи по-прежнему требуют непустой текст
до 500 символов. Структурированное изменение содержания или смена типа снимает исключение.
Никакие AI, обрезание, разделение по словам или синтетические краткие названия
при миграции не используются. Уточнение старых labels самим автором — задача
следующего UX-этапа; до этого прежние интерфейсы продолжают показывать точный текст.

Штатный runner применяет миграцию один раз и проверяет checksum. Дополнительно
SQL допускает повторное выполнение: backfill касается только отсутствующего
`label`, seed каталога не перезаписывает названия и отключение типов. Повторение
не создаёт Signals, награды или события и не переписывает структурированные записи.

## Неизменные границы

Все шесть вариантов видимости и состояния `active/closed/archived` сохранены.
`network_blind` разрешён только `need/have`, независимо от расширения каталога.
Чтение профиля и Exchange сохраняет текущие фильтры доступа, анонимности и
активности. Данные чувствительных типов не публикуются автоматически.

Relay продолжает ссылаться на те же UUID и раскрывать участников только после
взаимного согласия. Он не превращён в универсальный Connection. `/need` не меняет
UI или API. Триггер onboarding по-прежнему награждает только первые `need/have`,
в той же транзакции с записью и аудитом. Новые типы не создают mint.

`PROFILE_SIGNAL_KINDS` и `LegacyProfileSignalKind` описывают только текущий UI
из четырёх категорий. Доменный `ProfileSignalKind` — машинный ключ каталога;
проверка синтаксиса сама по себе не означает существование или включённость типа.

## Проверка миграции

`exchange-signals.integration.test.ts` принимает только `SIGNAL_TEST_DATABASE_URL`
на `127.0.0.1` с БД `signal_tests` и создаёт отдельную временную схему. Проверяет
реальный переход прежней схемы, IDs/текст/состояния, повторное применение,
каталог, оба пути создания, Relay, приватность и конкурентные награды.
`onboarding-quests.integration.test.ts` также применяет A1 поверх своих исторических
fixtures, сохраняя отдельную БД `onboarding_tests`. Эти тесты не используют
production `DATABASE_URL`.

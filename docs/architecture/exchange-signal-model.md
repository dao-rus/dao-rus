# Модель Signals: переход A1/A2

Смысл Exchange определяет [exchange-human-connectivity.md](exchange-human-connectivity.md).
Этот документ описывает хранение A1 и доменные пути/совместимость A2.

## Каталог типов

`signal_types(key, display_name, enabled)` — каталог типов существующего
`profile_signals`, а не отдельная система Signals. `key` — стабильный машинный
ключ (строчная латиница, цифры и `_`, до 64 символов). `display_name` — данные;
бизнес-правила не зависят от названия. Использованный ключ защищён внешним ключом.

Начальный набор: `need`, `search`, `can`, `have`, `want`, `know`, `skill`, `doing`,
`idea`, `dating`. Новый тип добавляется записью каталога, без расширения SQL CHECK
или TypeScript union. Административного интерфейса на A1 нет.

Отключённый тип запрещает создание новых Signals. Уже существующие записи
сохраняются и могут читаться и архивироваться по прежним правилам. Изменение типа
записи также требует разрешённого типа. Проверка каталога блокирует строку `FOR SHARE`
до конца транзакции создания; такую же проверку выполняет DB-триггер для SQL-писателей.

## Содержание и совместимость

Канонические поля `profile_signals`:

- `label` — обязательное ядро, 1–120 символов, непустое после `btrim`;
- `description` — опциональный контекст, до 10000 символов; отсутствие — `NULL`;
- `legacy_body` — признак дословного содержания из прежнего ввода одним `body`.

`body` остаётся совместимым представлением для профиля, Exchange, сообществ и
Relay. Для структурированной записи это `label` и, при наличии описания,
два перевода строки + `description`. BEFORE-триггер синхронизирует представление,
а CHECK проверяет равенство; расходящиеся версии содержания не допускаются.
Изменять `body` структурированной записи напрямую запрещено. Изменения
`label/description` автоматически обновляют `body`.

`createProfileSignalWithDatabase` / `createProfileSignal` — доменный путь создания
структурированных записей любого включённого типа. Возвращает UUID и, если
положено, результат прежней onboarding-награды. Каталог читается через
`listSignalTypesWithDatabase` / `listSignalTypes`.

`addProfileSignalWithDatabase` / `addProfileSignal` сохраняют контракт старого
редактора и `/need`: тип, `body` до 500 символов, видимость, результат награды.
Этот адаптер поддерживает только прежние четыре типа. Триггер принимает такие
body-only INSERT и UPDATE старых записей и дословно переносит их в `label` с
`description=NULL` и `legacy_body=true`. Новые категории должны использовать
структурированный путь. Текущий UI не расширяется.

## Перенос старых записей

Миграция `032_exchange_signal_types.sql` копирует старый `body` **целиком** в
`label`, оставляет `description=NULL` и отмечает `legacy_body=true`. UUID,
авторы, видимость, состояния, timestamps и ссылки `relay_encounters` сохраняются.
Перенос охватывает также закрытые и архивные записи.

Принципиальное ограничение: у старого свободного текста нельзя автоматически
получить краткое семантическое ядро без интерпретации или потери содержания.
Поэтому старые labels являются временными дословными формулировками и могут
превышать 120 символов. Даже исторические пустые/длинные строки, разрешённые
прежней SQL-схемой, сохраняются. Исключение применяется только к записям с
`legacy_body=true`; новые body-only записи по-прежнему требуют непустой текст
до 500 символов. Структурированное изменение содержания или смена типа снимает исключение.
Никакие AI, обрезание, разделение по словам или синтетические краткие названия
при миграции не используются. Уточнение старых labels самим автором — задача
следующего UX-этапа; до этого прежние интерфейсы продолжают показывать точный текст.

Штатный runner применяет миграцию один раз и проверяет checksum. Дополнительно
SQL допускает повторное выполнение: backfill касается только отсутствующего
`label`, seed каталога не перезаписывает названия и отключение типов. Повторение
не создаёт Signals, награды или события и не переписывает структурированные записи.

## Неизменные границы

Все шесть вариантов видимости и состояния `active/closed/archived` сохранены.
`network_blind` разрешён только `need/have`, независимо от расширения каталога.
Чтение профиля и Exchange сохраняет текущие фильтры доступа, анонимности и
активности. Данные чувствительных типов не публикуются автоматически.

Relay продолжает ссылаться на те же UUID и раскрывать участников только после
взаимного согласия. Он не превращён в универсальный Connection. `/need` не меняет
UI или API. Триггер onboarding по-прежнему награждает только первые `need/have`,
в той же транзакции с записью и аудитом. Новые типы не создают mint.

`PROFILE_SIGNAL_KINDS` и `LegacyProfileSignalKind` описывают только текущий UI
из четырёх категорий. Доменный `ProfileSignalKind` — машинный ключ каталога;
проверка синтаксиса сама по себе не означает существование или включённость типа.

## Проверка миграции

`exchange-signals.integration.test.ts` принимает только `SIGNAL_TEST_DATABASE_URL`
на `127.0.0.1` с БД `signal_tests` и создаёт отдельную временную схему. Проверяет
реальный переход прежней схемы, IDs/текст/состояния, повторное применение,
каталог, оба пути создания, Relay, приватность и конкурентные награды.
`onboarding-quests.integration.test.ts` также применяет A1 поверх своих исторических
fixtures, сохраняя отдельную БД `onboarding_tests`. Эти тесты не используют
production `DATABASE_URL`.

## Доменный контракт A2

`apps/core/src/lib/signals.ts` — универсальные типы, нормализация, lookup каталога,
создание, чтение и архивирование. `Signal` содержит `id`, `ownerId`, `typeKey`,
`label`, `description`, `visibility`, `status`, `legacyBody`, `createdAt`, `updatedAt`.
Он не содержит `body`. `ownerId` может быть `NULL` в анонимной выдаче.

`requireEnabledSignalTypeWithDatabase` проверяет синтаксис машинного ключа и
включённую запись каталога. Создание удерживает `FOR SHARE` в той же транзакции
до записи Signal, аудита и получения onboarding-feedback.

`createSignalWithDatabase` / `createSignal` принимают `typeKey`, `label`, опциональный
`description` и `visibility`; возвращают канонический `signal` и возможную
onboarding-награду. Ключи новых типов не требуют правки доменного TypeScript-кода.
Схема и миграция A1 не меняются.

### Чтения и доступ

Контекст viewer передаёт доверенный адаптер из текущей сессии, как в прежних
функциях Core; viewer ID не следует брать из пользовательской формы.

- `listParticipantSignalsWithDatabase` — активные Signals профиля любого типа.
  Автор видит свои записи всех visibility. Другой вошедший участник получает
  только `public/members`. Неактивные `closed/archived` можно запросить только
  для собственного профиля; чужие неактивные записи возвращают пустую выдачу.
- `listNetworkSignalsWithDatabase` — активная витрина выбранного типа, с прежними
  `public/members/network_blind`, порядком по created_at/id и LIMIT 100.
  `NetworkSignal` добавляет `mine` и допустимого автора. Для `network_blind`
  **даже в собственной сетевой выдаче** ownerId и author равны NULL; принадлежность
  своей записи обозначает только прежний `mine`. Редакция применяется как в SQL,
  так и при сборке результата. Скрытые владельцы не попадают в универсальный контракт.

Отключение типа по-прежнему запрещает новые записи, но не прячет существующие.
Оба чтения используют общий набор канонических колонок и mapper. SQL-поле `body`
не запрашивается; никакое чтение не сокращает унаследованный label.

### Адаптеры прежних интерфейсов

`signal-compat.ts` содержит список четырёх типов старых форм, нормализацию legacy
body и `signalBodyProjection`: label + опциональное описание через два перевода строки.
SQL-проекция A1 остаётся защищена своим триггером/CHECK, а интерфейсная проекция
строится из тех же канонических полей. Второго источника содержимого нет.

`profile-about.ts` сохраняет прежние экспорты как фасад совместимости:

- `addProfileSignal*` — body-only адаптер старых `/profile` и `/need`;
- `createProfileSignal*` — совместимый контракт A1 с `kind` и результатом `id/reward`,
  делегирующий универсальному `createSignal*`;
- `getProfileAbout*` и `getVisibleProfileAbout*` — прежние объекты UI над общим чтением;
- `archiveProfileSignal*` — тот же общий сервис архивирования.

`listExchangeSignals*` в Relay также является адаптером над универсальным сетевым
чтением. Encounter/message/reveal logic сохраняет прежний специальный контракт.
Тексты и дизайн страниц не меняются. Четыре категории остаются только в старых
формах, вкладках и счётчиках, а need/have — в специальных правилах Blind Relay
и onboarding. Они не ограничивают каталог.

### События и приватность

Существующее `participant.signal_created` сохраняет `signal_id`, `kind`, `visibility`.
Добавлены `type_key`, `status`, `legacy_body`, `content_source='label_description'`.
Событие ссылается на каноническую запись по ID; потребитель получает содержимое
через доменное чтение с соответствующим доступом. Label, description и body
не копируются в общий аудит: payload не создаёт дополнительный канал утечки
приватного содержимого. Это ссылка на состояние, а не неизменный снимок текста.

Onboarding по-прежнему определяется конкретными need/have first-action events
и DB-триггером. Другие типы не получают наград автоматически. Универсальных
Connections, AI, utility mint и новой policy engine в A2 нет.

## Пользовательский слой A3

`/exchange/new` получает типы из `signal_types` через доменный каталог A2.
Новая запись использует `createSignal`; уточнение по `?signal=<id>` — `updateSignal`.
Тип при редактировании не меняется. Адаптер берёт владельца из сессии;
доменный UPDATE блокирует только собственную активную запись. Редактирование
отключённого типа сохраняется, создание запрещено. Событие обновления содержит
ссылку и метаданные, не приватный текст; обновление не создаёт onboarding reward.

Профили читают `Signal` напрямую и показывают только заполненные категории.
Фасад `profile-about` может пропускать совместимую проекцию Signals для этих
страниц; остальные старые читатели сохраняют прежний контракт. Anchors
`signal-<key>`, архивирование, `/need` и Blind Relay сохранены.

Exchange использует `?type=<key>` и принимает прежний `tab`. Неизвестный ключ
возвращает default `need` (либо первый включённый тип, если need отключён).
Навигация строится из enabled каталога и не зависит от количества доступных или
скрытых записей. Это одна неразрывная полоса без переноса строки: на узком экране
она прокручивается вбок, а значок встаёт над подписью. Порядок вкладок смысловой —
порядок `signalPresentationDefaults` (`orderSignalTypes`), а не SQL-порядок по
ключу; типы, которых нет в подсказках, идут следом в порядке каталога. Значки —
встроенные SVG (`signal-type-icon.tsx`), чтобы не зависеть от набора глифов в
шрифтах устройства. Группы используются только в выпадающем списке формы;
группы и символы в `signal-presentation.ts` — только подсказки представления.
Неизвестные типы попадают в «Другие сигналы» с названием из каталога и общими
редактируемыми пояснениями. Они не требуют изменения центральных страниц.

Имена прежних четырёх категорий и CTA сохраняют ключи `exchange.tab_*` / `add_*`.
Остальные пояснения, примеры, placeholders, названия групп и оболочка формы
зарегистрированы в `interfaceTextFields`, доступны в `/admin/interface`.
Машинные ключи независимы от этих текстов.

Legacy label не делится и не сокращается. В форме короткий label пуст,
а исходный текст целиком предложен в description и отдельно доступен для сверки.
Сохранение выполняется только по действию владельца. Миграция
`033_signal_explicit_refinement.sql` не переписывает записи: она позволяет явно
снять marker даже при подтверждении неизменённого короткого label. Существующий
CHECK по-прежнему запрещает длинный label без legacy marker; проекция body остаётся
синхронизированной. Исторический ввод `/need` продолжает создавать legacy Signals.

Тип `dating` в интерфейсе называется «Ближе»: то, что нужно, но трудно сказать
при всех. Машинный ключ и `signal_types.display_name` не менялись; название,
пояснение и текст вкладки редактируются в `/admin/interface`. Форма и её
POST-адаптер допускают для него только `match_only` (default) и `private`:
запись «Ближе» не публикуется никогда, открытый запрос уместнее в «Ищу».
Существующие записи с другой видимостью не переписываются и читаются по A2.
Это консервативное ограничение текущего Web UX, не универсальная policy engine.

Вкладка `/exchange?type=dating` не вызывает сетевое чтение: она показывает
объяснение механики и только собственные записи зрителя. Подбор совпадений
и анонимный диалог по совпадению **не реализованы** — текст вкладки говорит об
этом прямо. Согласованный замысел следующего этапа: совпадение видят обе стороны
одновременно и без имён, разговор идёт анонимно с раскрытием по взаимному
согласию (как в Relay), для чего потребуется сущность пары записей. Правило
совпадения (ключ, выбранный автором, или смысловой подбор) ещё не решено.

## Каноническая карточка B1

`/exchange/<uuid>` — постоянный внутренний адрес Signal, не зависящий от типа,
формулировки или имени владельца. `signalHref` в `signal-presentation.ts`
используется в Exchange и обоих профилях. B1 не создавал новых таблиц;
внешняя карточка и реакции добавлены отдельным следующим этапом ниже.

`getSignalWithDatabase` / `getSignal` в `signals.ts` читают канонические поля
по UUID и доверенному viewer из сессии. Невалидный UUID, отсутствующая и
недоступная запись дают одинаковый `null`; Web-адаптер вызывает `notFound()`.
Гостевой read path ниже использует отдельную узкую проекцию и предикат доступа.

`visibility = public` буквально означает доступность без входа (см. ниже).
Другой вошедший участник получает активные public/members/network_blind;
владелец — свои записи всех visibility и состояний, как в чтении профиля A2.
Circle и match_only не получают нового канала доступа. Неактивная запись
остаётся доступна только владельцу, без действий редактирования/архивирования.

SQL-предикат активной видимой записи разделяют прежние чтения и permalink.
SQL-проекция и mapper identity разделяются с сетевой выдачей A2: network_blind
всегда имеет ownerId=NULL и author=NULL, в том числе у владельца. Страница не
передаёт Signal в клиентский компонент и дополнительно не выводит blind identity.
Отклик использует только существующий `/api/relay` для чужого активного need/have.
Раскрытие в Relay после взаимного согласия не меняет анонимность самой карточки.

Владельческие действия используют прежние редактор A3 и архивирование.
Legacy label отображается дословно, без использования body в качестве источника.
Отключение типа не убирает уже существующую допустимую карточку.

Недоступные гостю карточки имеют нейтральные metadata и robots noindex/nofollow.
Гостевые карточки могут содержать тип и сокращённый label в OpenGraph,
но не владельца или description; robots остаётся noindex/nofollow.

## Публичная карточка и лайк Signal

Активный Signal с `visibility = public` открывается по `/exchange/<uuid>` без входа:
гостевое чтение проверяет только `status = 'active'` и `visibility = 'public'` при
каждом запросе. Отдельного согласия на внешнюю ссылку нет: выбирая `public`, автор
публикует запись, включая своё имя, для всех. Гостевая проекция содержит только
`id`, тип, `label`, `description` и имя автора — без идентификатора владельца,
статуса и служебных полей. Смена видимости на другую или архивирование сразу
закрывают карточку для гостей. `members`, `private`, `circle`, `match_only`,
`closed` и `archived` остаются недоступными гостю; `network_blind` в v1 гостям
не открывается. Гость видит самодостаточную карточку без меню Core, может
пользоваться «Поделиться» (Web Share API, Telegram, ВКонтакте, e-mail, копирование
ссылки) и перейти на «ДАО Русь». Лайка, отклика, профиля автора, редактирования и
DARUS у гостя нет. Индексирование карточек выключено.

Колонка `external_share_enabled` (миграция 035) устарела и не используется: код её
не читает и не пишет, она не влияет ни на доступ, ни на Share, ни на UI. Триггер
`clear_signal_external_share` лишь продолжает обнулять её в БД.

Кнопка «Поделиться» внутри Core показывается для активных Signals, которые может
открыть кто-то ещё (`public`, `members`, `network_blind`); для `private`, `circle`
и `match_only` её нет. Действия карточки по ролям: чужой Signal — «Перейти к автору»,
«♥ N», «Поделиться»; владелец — «Редактировать», «Архивировать», «Поделиться»;
`network_blind` — «Откликнуться», «♥ N», «Поделиться»; гость — «Поделиться» и
«ДАО Русь».

`signal_reactions` хранит историю обычного лайка («♥») конкретного Signal.
Частичный уникальный индекс допускает один активный лайк участника, снятие
заполняет `revoked_at`, повторные команды идемпотентны. Собственный Signal лайкнуть
нельзя. Лайк не создаёт `reputation_signals` (Карму), Connection или начисление
DARUS и не влияет на permissions. Гость лайкнуть не может.

Внутреннее «Отправить участнику» остаётся отдельным будущим flow согласия
адресата. `darus_ledger` сейчас хранит положительные начисления и не определяет
добровольный debit/transfer в системный sink с защитой баланса и идемпотентностью;
поэтому «Поддержать сеть» не выводится на карточке.

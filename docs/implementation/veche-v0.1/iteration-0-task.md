# Итерация 0 — сверка действующего Вече с целевой моделью

Статус: задание Codex, только чтение и отчёт. Дата: 2026-10-09.

## Обнаружено прямым чтением GitHub (важная корректировка исходных предположений)

Раздел `/veche` — **не просто заглушка**. Уже существуют:
- `apps/core/src/app/veche/page.tsx`: список предложений, форма создания, форма сбора подписей, ссылка на администрирование.
- `apps/core/src/app/api/proposals/route.ts` и `apps/core/src/lib/proposals.ts`: создание предложений, членский допуск, журнал `proposal.created`.
- `apps/core/src/app/api/veche/route.ts` и `apps/core/src/lib/veche-signatures.ts`: создание подписного созыва, подписи, отзыв, вызов SQL `veche_refresh_call`, настройки долей и срока.
- `apps/core/src/lib/veche-polls.ts`: открытое/тайное голосование, право голоса, закрытие, кворум и публичные проекции.
- `apps/core/src/lib/eligibility.ts`: создание предложений сейчас зависит от `membershipStatus === 'participant'`.
- `apps/core/package.json`: Next.js 16, PostgreSQL, Vitest, TypeScript; есть worker уведомлений.

Следовательно, **не создавать параллельные Proposal/Support/Veche/Vote и собственный voting engine до аудита**. Документ `docs/architecture/veche-mvp-v0.1.md` описывает логические сущности, не предписывает новые таблицы.

## Цель

Проверить, какие элементы уже реально работают и какие точечные изменения нужны для **анонимного инициирования + автоматического созыва** при согласованном пилотном правиле: один независимый человеческий подтверждающий контакт для допуска, пять независимых поддержавших помимо автора, без автоматической блокировки дизлайками.

## Задания Codex

1. Прочитать документы `docs/governance/anonymous-automatic-veche.md`, `docs/architecture/veche-mvp-v0.1.md`, `docs/architecture/telegram-first.md`, `docs/ontology/ontology.md`, `docs/architecture/decision-making-principle.md`.
2. Найти все миграции, функции PostgreSQL, ограничения, триггеры и тесты, относящиеся к `proposals`, `proposal_signatures`, `proposal_votes`, `veche_settings`, `veche_refresh_call`, `veche_eligible`. Объяснить реальный переход `collecting → called`, конкурентную безопасность и обработку срока.
3. Проверить интерфейсы `/veche`, `/veche/[id]`, все API и админ-экраны, worker и Telegram announcement: какие операции уже доступны и какие фактически автоматизированы.
4. Установить все поверхности возможной утечки автора (SQL выборки, listProposals, ParticipantName, PollView.authorId, страницы, API, events, Telegram, админка, логи). Предложить единую серверную политику публичных проекций и ограничение доступа к приватной связи.
5. Найти существующую модель графа человеческих подтверждений и проверить, можно ли отделить **допуск к созыву** от текущего `membershipStatus`, не ломая старые права и голосования.
6. Сопоставить текущие настраиваемые доли порогов и круги `dao/city` с пилотным абсолютным порогом 5. Предложить минимальную совместимую настройку, без жёсткого кодирования числа в SQL.
7. Сопоставить имеющееся голосование Core с документированной Telegram-first моделью. Явно указать, где документы расходятся с реализованным кодом, и какой путь требует меньше переделок.
8. Запустить только безопасные локальные проверки, если окружение доступно (`typecheck`, `test`); не использовать реальные секреты, не менять БД или production. Если запуск невозможен — указать причину, не объявлять тесты успешными.
9. Подготовить **один** отчёт в `docs/implementation/veche-v0.1/iteration-0-report.md`, содержащий: (а) карту файлов и таблиц; (б) подтверждённые возможности; (в) пробелы и риски; (г) точечный план итераций 1–N с зависимостями; (д) список существенных архитектурных развилок, требующих решения; (е) результаты реально запущенных проверок. Указать конкретные пути и функции.

## Ограничения

- Не изменять код, миграции, конфигурацию, канонический Кодекс или production.
- Допускается создание только файла отчёта и коммит отчёта в рабочую ветку; не сливать в main без отдельного указания.
- Не создавать дублирующие таблицы и новые сущности «на всякий случай».
- Не переходить к итерации 1 без моего разбора отчёта.
- Отчёт должен быть коротким, проверяемым и без пересказа всей философии ДАО.

## Критерий приёмки

После отчёта должно быть понятно, какие **конкретные существующие механизмы** расширять, где менять проверки доступа, как обеспечить неразглашение автора, как переиспользовать механизм подписей и автоматического перехода, и какие тесты защищают эти свойства.

# Приёмная: управляемые приглашения, этап 4

Продолжает [архитектуру](../architecture/reception-miniapp-onboarding.md) и
[доставку этапа 3](reception-publication.md). Новых сервисов, очередей и ролей нет.
Миграция 054 добавляет к `reception_application_deliveries` поля автора/времени
решения и форума назначения; используется существующий `kind='invitation'`.

## Решение и полномочия

Кнопка «Пригласить» в `/admin/reception` вызывает POST `/api/admin/reception`
с `action=invite`. Сервер проверяет сессию, origin и действующий явный allowlist
`ADMIN_PARTICIPANT_IDS`, как остальные действия Хранителя. Обычные участники,
включая пользователей с полномочиями только на награды, приглашать не могут.
Назначение Хранителя/уполномоченного администратора использует существующий
порядок предоставления доступа к управлению Core.

Транзакция под общей блокировкой Telegram ID создаёт решение, invitation-row
и `reception.invitation_requested` в `events`. `requested_at` и `requested_by`
сохраняют решение независимо от доставки. Повторные/конкурентные нажатия
не создают новую задачу или второе решение. HTTP не обращается к Telegram.
Worker не обрабатывает invitation-row без `requested_at`. Публикация и приглашение
независимы; изменение анкеты не повторяет приглашение.

## Фоновая отправка

Используются общий движок этапа 3 в `reception-publication.ts`, существующий
`notification-worker` и **существующий** флаг `TELEGRAM_GUARDIAN_INVITES_ENABLED`
(по умолчанию false). Флаги публикации и Mini App не меняются. Выключенный флаг
оставляет принятое решение в pending.

Нужны Reception bot token, forum chat ID и действующая HTTPS-ссылка
`TELEGRAM_FORUM_INVITE_URL` на t.me/telegram.me. Новые ссылки не создаются,
старые не отзываются. Перед каждой отправкой выполняется свежий getChatMember:
проверяются status и совпадение user.id с идентичностью заявки. restricted
учитывается по is_member; creator/administrator/member означают членство.
Reception bot должен быть администратором форума: для других пользователей
Telegram [гарантирует getChatMember только в этом случае](https://core.telegram.org/bots/api#getchatmember).

Текст сообщения редактируется в существующем `/admin/interface`:
`reception.invitation.message`. Действующая ссылка добавляется worker автоматически;
сообщение отправляется обычным текстом без HTML/Markdown-разбора.

Неудача чтения членства не доказывает отсутствие человека: задача остаётся pending,
сообщение не отправляется, чтение повторяется с задержкой и учётом retry_after.
Telegram не предоставляет транзакцию между проверкой и отправкой: человек может
вступить в этом промежутке. Подтверждённое членство отменяет отправку, не создавая
Participant и не изменяя membership_status. Событие фиксирует наблюдение, не дату вступления.

SKIP LOCKED/claim token и session advisory lock переиспользуют правила этапа 3.
Перед sendMessage отдельно фиксируются attempted_at и ревизия. При успехе
сохраняются личные chat/message ID. Текст приглашения/ссылка не копируются
в attempted_text или events; токен, initData и сырые исключения не логируются.
Результат и `reception.invitation_result` фиксируются одной транзакцией.
Сбой записи результата после возможной отправки оставляет durable claim для сверки.
Timeout, потеря ответа, 5xx и непонятный результат не разрешают автоматический повтор.
Явные отказы Telegram допускают повтор с задержкой от минуты до часа и не меньше
retry_after; перед ним снова проверяется членство. Доставленное приглашение
не редактируется и не отправляется заново при правках анкеты.

## Независимые состояния и ручная сверка

| Измерение | Учёт / отображение |
| --- | --- |
| Решение | Без invitation-row — не принято; requested_at — принято «Пригласить», автор в requested_by/events |
| Доставка | pending — «Ожидает отправки»; processing — обработка; delivered — «Приглашение отправлено»; needs_review — «Требует проверки» |
| Отправка не требуется | failed + already_joined — «Уже вступил»: терминальная пропущенная операция, не ошибка Telegram |
| Членство | Свежий getChatMember перед отправкой; отдельно последнее participant_forum_onboarding наблюдение через Telegram identity |
| Получение/прочтение | Не устанавливается по sendMessage; события «получил»/«прочитал» не создаются |

Присвоение статуса участника ДАО не следует ни из решения, ни из отправки, ни
из присутствия в форуме. already_joined не вызывает новых приглашений после выхода.
Зависшие claims до attempted_at возвращаются в pending, после него — needs_review;
восстановление фиксируется в `reception.invitation_recovered`.

Inspect/confirm/retry принимают серверный selector `kind=invitation`, проверяют
права и version delivery. Получатель определяется заявкой, пользовательские chat ID
не принимаются. Административная сверка записывается в `reception.delivery_review`
с kind, actor, version и отдельной отметкой ручной проверки.
Хранитель может подтвердить **отправку** по достоверным свидетельствам и известному
оригинальному message ID либо подтвердить отсутствие сообщения и разрешить повтор.
Без отдельной отметки операция отклоняется. API обычного Reception bot не даёт
достоверный поиск истории личного диалога по неизвестному ID. Если исход/ID
невозможно установить, оставить needs_review, не подставлять фиктивный ID.

## Совместимость с прежним auto-invite

Для заявителей `checkForumAndInvite` наблюдает членство, но передаёт inviteSource=null,
даже после решения Хранителя. Отправкой управляет только outbox. Проверка наличия
заявки и прежний check/send выполняются под той же блокировкой Telegram ID,
что сохранение анкеты. Это исключает отправку после подачи по устаревшему чтению.
Вложенный observeForumMembership использует то же соединение, без второго pool slot.
Как в этапе 3, session locks требуют прямого pg.Pool; transaction-mode PgBouncer не подходит.

Если прежний путь начал отправку до подачи, сохранение ждёт его окончания.
При решении Хранителя read-only resolver проверяет participant_forum_onboarding:
прежняя подтверждённая отправка или попытка без подтверждённого отказа создают
needs_review с legacy_invitation_sent/legacy_invitation_unknown. Повтора нет.
Подтверждённый старый blocked допускает обычную очередь после явного решения.
Конфликт Telegram identity отклоняет решение без задачи. Для людей без заявки
прежний порядок сохраняется. Прямое вступление, chat_member ingestion, webhook,
relay и Dev auth не изменены; фактическое вступление обрабатывается прежними правилами.

## Проверка и этап 5

`reception-invitations.integration.test.ts` защищает полномочия, решения/конкуренцию,
два worker, membership, отказ/429, неизвестную отправку, перезапуски, audit rollback,
ручное восстановление, сохранность профилей и гонку legacy с подачей анкеты.
Используется изолированная PostgreSQL reception_tests и отдельный Telegram ID.

Перед production-включением проверить отдельный bot/forum: действующую ссылку,
getChatMember, личный чат, successful send и 403/429, обрыв ответа, перезапуск,
ручную сверку, already_joined и legacy_unknown. Флаги включать только после
самостоятельной проверки и отдельного разрешения.
Этап 5 должен связать анкету с Participant после фактического вступления по проверенному
Telegram ID, сохраняя самостоятельно изменённые поля и устраняя конфликты идентичностей.
Проверить прямой вход без анкеты и повторные/запоздалые chat_member updates, включая уход.
Сквозной прогон Mini App → публикация → relay → решение → приглашение → вступление →
профиль требует настоящих Telegram Android/iOS/Desktop клиентов.

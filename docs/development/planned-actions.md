# Планируемые действия

Этот файл фиксирует согласованные, но ещё не реализованные изменения DAO Rus. Это рабочий backlog, а не описание текущего состояния системы.

## Награды / отбор кандидатов (13 октября 2026)

- [ ] **Срочно: отмена ошибочного массового добавления кандидатов в черновике выпуска.** В интерфейсе выпуска добавить действие «Очистить список кандидатов» с подтверждением и/или «Отменить последнюю выборку»; не затрагивать уже завершённые выпуски и другие награды. Явно подписать текущую операцию фильтра как «Добавить к списку», поскольку она не заменяет старую выборку. Сохранить возможность исключить одного кандидата. Не изменять историю награждений; до реализации определить безопасную семантику очистки и тесты.

- [ ] **Фильтр кандидатов по исторической дате вступления в черновике выпуска награды.** На странице `/admin/awards/[awardId]/batches/[batchId]` добавить два поля «Вступил с» / «Вступил по» (обе границы включительно), чтобы учредитель мог сформировать выборку за период, например 13.10.2023–13.04.2024 для Знака Первой волны.
  - Использовать достоверную дату первого вступления/участия из уже существующих импортированных Telegram-данных, а не `participants.created_at` (это дата создания профиля в Core). До реализации проверить, где хранится историческая дата и какова её достоверность; не подменять неизвестную дату датой импорта.
  - Показывать в результатах дату и её источник либо «дата неизвестна»; не исключать навсегда людей без даты: сохранять ручное добавление кандидатов и дочеканку по Уставу наград, п. 8.
  - Фильтр работает вместе с существующими фильтрами (город, интересы, верификация, статус); до окончательного выпуска отображать количество найденных и давать просмотреть/исключить кандидатов.
  - Не менять критерии самой награды и не выпускать её автоматически по одному лишь совпадению даты. Реализация — отдельная задача, пока не выполнена.

## Telegram / онбординг

- [ ] **Интегрировать «Приёмную ДАО Русь» с DAO Core и использовать её для мягкой социализации участников.**
  - Разделить роли Telegram-ботов:
    - **«Приёмная ДАО Русь»** — вход, ориентация, онбординг и социализация;
    - **DAO RUS Dev bot** — повседневные рабочие функции Core, включая линию «Мне нужно».
  - Оба бота должны работать через общий слой интеграции / Core API и общую связь `telegram_user_id ↔ core_user_id`, без независимых пользовательских сущностей.
  - Для пользователя, который уже зарегистрирован в Core, проверять членство в основном Telegram-форуме ДАО.
  - Если пользователь есть в Core, но не состоит в форуме, «Приёмная» должна отправить мягкое персональное приглашение вступить.
  - После вступления фиксировать завершение этого шага онбординга и прекращать приглашения.
  - В перспективе поддержать обратный маршрут: участник форума без профиля Core → предложение зарегистрироваться в Core.
  - Не делать членство в форуме обязательным условием доступа к Core: задача механизма — достраивать пропущенный социальный маршрут, а не создавать жёсткую воронку.

- [ ] **Развить «Приёмную» в бота-хранителя жизненного цикла участника.**
  - Публично «Приёмная ДАО Русь» остаётся точкой входа, а внутренне получает роль **Хранителя** — агента сопровождения участника на всём пути в ДАО.
  - Отслеживать ключевые переходы: вход → онбординг → включение в социальные контуры → участие → выпадение из активности → явный уход → возможный возврат.
  - Для новых участников: встречать, объяснять устройство ДАО, подсказывать незавершённые шаги онбординга и мягко направлять к форуму, профилю и другим базовым контурам.
  - Для участников, которые выпадают из связности: замечать незавершённый онбординг, неотвеченные запросы, отсутствие включённости в основные контуры и предлагать следующий естественный шаг без давления.
  - При явном уходе из форума / сообщества: по возможности проводить короткий **exit-feedback / exit interview** — спрашивать причину ухода и фиксировать её как сигнал о качестве социальной архитектуры ДАО.
  - Поддержать типовые причины ухода: «неинтересно», «слишком много шума», «непонятно, что делать», «не нашёл людей / пользы», «не согласен с принципами», «конфликт», «другое».
  - Агрегировать обезличенные причины ухода и использовать их как метрики качества онбординга, связности и полезности ДАО.
  - В перспективе поддержать добровольный **win-back**: если устранена причина ухода, сообщать об этом только тем, кто сам разрешил такие уведомления.
  - Принцип Хранителя: не оценивать участника и не контролировать его поведение, а выявлять места, где ДАО не смогло нормально встретить, связать, поддержать или удержать человека.

- [ ] **Различать добровольный уход из Telegram-форума и институциональное исключение из ДАО.**
  - Исключение — не Telegram-статус, а правовой статус, который возникает только на основании действующего решения Вече.
  - Потеря членства в Telegram-форуме сама по себе не означает исключение из ДАО.
  - Если человек перестал состоять в форуме и действующего решения Вече об исключении нет, считать это добровольным уходом для целей жизненного цикла и Хранителя.
  - Если технически участника удалил администратор без решения Вече, не присваивать статус `excluded`; при необходимости фиксировать это отдельно как технический факт удаления из форума.
  - Для определения институционального статуса использовать Core как источник истины: факт потери forum membership → проверка действующего решения Вече → `excluded` или `left`.
  - Ввести отдельные события уровня Core, например `forum.left`, `forum.removed` и `membership.excluded`, сохраняя источник и время события.
  - Добровольный уход может запускать exit-feedback; исключение не должно трактоваться как обычный незавершённый онбординг и не должно автоматически вести к повторному приглашению.
  - Отдельно проверить на production, что реальные выходы из форума действительно приходят в webhook и фиксируются в БД.

- [x] **Тариф и награды Вече (Q-008):** атомарный платный созыв, точная невозвратная раздача, версионная чеканка и лимит организатора. Выключены до настройки чисел.

- [x] **Анонимный инициатор Вече (Q-010):** фиксированный выбор видимости, одна серверная проекция, безопасные события и личная книга тарифа.

- [x] **Минимум подписей и снимок Вече (Q-011):** max(минимум, доля круга), минимум 5 по умолчанию, неизменяемые правила и backfill без пересчёта начатых сборов.

- [x] **Пустые вопросы Вече (Q-009):** открытые отметки, отключённые до настройки пороги, отмена чеканки, сигналы только по публичным вопросам и гласная заморозка права созыва решением Вече.

- [x] **Участник без города (Q-013):** единое объяснение блокировки и ссылка на поле города на трёх страницах Вече; чтение и итоги доступны.

- [x] **Понятный раздел Вече и пошаговый созыв (Q-012):** шесть серверных шагов, группы вопросов, свой голос только по сессии, итоги в процентах и счёт доступных действий в меню.

Идеи ниже — на отдельную проработку; пока не считать утверждённой схемой реализации.

- [ ] **Переводы DARUS между участниками.**

  - Для каждого перевода сохранять отправителя, получателя, сумму, время и при необходимости основание/комментарий.
  - История переводов должна быть частью аудируемого ledger, а не изменением баланса без следа.

- [ ] **Целевой фонд, связанный с голосованием Вече.**

  - Голос и вклад не должны быть одним действием: участник может поддержать инициативу голосом, вкладом DARUS, обоими способами или ни одним.
  - Назначение фонда связывается с конкретной инициативой/целевой деятельностью.

- [ ] **Проектное голосование с утверждением проекта и проектного лидера.**
  - Поддержать вариант голосования, в котором Вече одновременно рассматривает сам проект и кандидатуру его проектного лидера.
  - Варианты/формулировки предложения можно изменять в ходе обсуждения.
  - Каждая версия предложения и вариантов должна сохраняться в истории.
  - Если существенное изменение произошло после уже поданного голоса, участнику нужно явно показать факт изменения и дать возможность подтвердить прежний голос или изменить его; нельзя молча переносить старый голос на новую формулировку.

## Обмен / торговля между участниками

Идея на отдельную проработку (9 октября 2026); схема не утверждена, кода нет. Решения о данных и деньгах участников выносятся Вану до кода.

- [ ] **Отдельная страница «Магазин» — торговля между участниками.**
  - Нужна, потому что обмен товарами и услугами — естественная часть связности; но это самая опасная для идеи функция, поэтому проектируется отдельно и осторожно.
  - Предварительная оценка: не разрушительна, если Ядро остаётся витриной и связью, а сделка и оплата происходят между людьми. Разрушительна, если Ядро становится торговой площадкой с деньгами внутри.
  - **Рамка, предложенная к решению Вана:**
    - Магазин вырастает из «Обмена» (типы «Есть», «Могу», «Умею»), а не строится параллельно: запись с ценой и условиями, тот же отклик, те же пометки видимости.
    - По умолчанию — «Только ДАО»; витрина для посторонних не включается.
    - Оплата вне Ядра, напрямую между людьми. Ядро не держит деньги, не делает эскроу, не берёт комиссию и не становится стороной сделки.
    - DARUS не покупаются за деньги и не продаются за деньги. Иначе право созыва вече и награды за пользу становятся покупаемыми (Устав созыва вече, п. 4.5 и 9).
    - Разговор о сделке идёт в Telegram; Ядро хранит только структурированный факт (что предложено, кому, чем закончилось).
    - Итог сделки связывается с уже существующей отметкой о хорошем опыте взаимодействия, а не с новой системой рейтингов продавцов.
    - Спорам нужен путь: сообщить Хранителям о проблеме, без скрытых наказаний; решение и санкции гласные.
  - **Что нужно решить до кода:**
    - допускается ли цена в DARUS (взаимные расчёты внутри ДАО) или только договорная цена вне Ядра;
    - что храним об итоге сделки и кому это видно (минимум: факт и отметка, без сумм);
    - что считать запретным товаром и кто следит;
    - юридический статус: Ядро как витрина объявлений против посредника в расчётах — разница существенная, нужна консультация юриста до включения любых платежей;
    - награда DARUS за сделку: по умолчанию её нет, чтобы не поощрять торговлю ради награды; связь с идеей «чеканка обоим за взаимный хороший итог» решается вместе.

## ДАО Земля / запуск и распространение

- [ ] **Запустить ДАО Земля через личные международные связи участников ДАО Русь.**
  - На этапе запуска каждый участник ДАО Русь должен отправить ссылку на ДАО Земля как минимум одному лично знакомому иностранцу.
  - Основной принцип распространения — не холодная реклама, а перенос доверия через уже существующую человеческую связь: участник приглашает конкретного человека, которого знает сам.
  - Считать это стартовым механизмом международного bootstrap: ДАО Русь выступает первоначальным ядром связности, из которого ДАО Земля расширяется наружу через реальные межличностные мосты.
  - Продумать простой интерфейс/сценарий приглашения и способ измерять, сколько приглашений привело к регистрации и дальнейшему участию, без превращения механизма в спам или реферальную гонку.

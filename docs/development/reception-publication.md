## Включение и фоновые задачи

Доставка исполняется существующим `notifications:worker`. Отдельный флаг
`TELEGRAM_RECEPTION_PUBLICATIONS_ENABLED=true` разрешает обработку и восстановление
зависших задач. По умолчанию он выключен, независимо от
`TELEGRAM_RECEPTION_MINI_APP_ENABLED`. Нужны штатные `TELEGRAM_RECEPTION_BOT_TOKEN`,
`TELEGRAM_FORUM_CHAT_ID`, `TELEGRAM_RECEPTION_TOPIC_ID`. Для General (topic 1)
`message_thread_id` не передаётся. Отключение флага не отменяет уже начатый запрос.
Флаг нужно менять в окружении worker; один worker-процесс должен быть постоянно запущен.
Новый сервис не добавлен. При выключенном флаге существующие уведомления работают как раньше.

## Идентичность и приватность

API сохраняет только нормализованные имя и username из проверенного Reception
`initData`, без полного профиля или сырого `initData`. Клиент не может прислать имя.
Для старых заявок worker получает имя через read-only `getChat`, проверяя private
тип и совпадение ID. Неудача этого чтения безопасно откладывает отправку.
Профили и external identities Core не обновляются.

Публикация — plain text, без `parse_mode` и клиентских entities. Возраст включается
только при `publish_age=true`. Доступ к журналу использует существующие prototype
права управления (`ADMIN_PARTICIPANT_IDS`), как другие разделы Хранителя.
Даже этому пользователю возраст без согласия на публикацию не выдаётся.
Снимок попытки содержит только предназначенный для публикации текст. Для ручной
сверки журнал показывает его с удалённой строкой исторического возраста.
Полный снимок не выдаётся в административный API. Отзыв согласия скрывает возраст в журнале сразу,
а удаление возраста из Telegram подтверждается отдельным успешным редактированием.
При неизвестном результате удаления требуется срочная ручная сверка Хранителем.

## Состояния и резервирование

Сохраняются названия миграции 052: `pending`, `processing`, `delivered`, `needs_review`.
Публикация не использует `failed`; этап 4 использует его для пропущенного
приглашения с безопасной причиной already_joined. См. [управляемые приглашения](reception-invitations.md).

- `pending`: допустимая первая отправка/повтор после явного отказа Telegram.
- `processing`: атомарное резервирование CTE `FOR UPDATE SKIP LOCKED`, уникальный
  claim token. Два процесса не резервируют одну задачу.
- `delivered`: Telegram подтвердил message ID и chat ID либо Хранитель вручную
  подтвердил конкретную попытку. Сохраняется опубликованная ревизия.
- `needs_review`: неизвестный результат; автоматическая отправка остановлена.

Перед сетевым запросом отдельно фиксируются `attempted_at`, ревизия, текст и
назначение. Сбой до этой отметки позволяет безопасный повтор; после неё нельзя
доказать отсутствие отправки. Зависшие более 10 минут claims без отметки возвращаются
в pending, с отметкой — в needs_review. Claim token ограждает от устаревшего worker.

Session advisory lock на той же Telegram-идентичности, что у записи анкеты,
сериализует снимок/отправку/фиксацию с правками и ручным восстановлением.
Восстановление не трогает активный sender с этой блокировкой. Запрос Telegram
ограничен 8 секундами. Используется прямое соединение pg.Pool: transaction-mode
PgBouncer несовместим с session advisory locks без изменения реализации.

Только явный ответ Telegram `ok:false` с кодом 400/401/403/404/429 разрешает
автоматический повтор. Задержка растёт от 60 секунд до часа и не меньше `retry_after`.
Timeout, исключение сети, 5xx, непонятный ответ или потеря записи результата
не разрешают повторную отправку. Ответы/exception descriptions не сохраняются:
только короткие безопасные коды. HTTP доступность Telegram не доказывает недоставку.

Неизменённая анкета сохраняет ревизию и не отправляется повторно. После изменения
опубликованной анкеты worker вызывает `editMessageText` с тем же message ID;
новое сообщение не создаётся. `message is not modified` подтверждает применённую
редакцию. Неизвестное редактирование требует сверки; даже разрешённый вручную
повтор остаётся редактированием. Удалённое исходное сообщение не заменяется
автоматически. Смена настроенной темы останавливает закреплённую доставку:
сначала восстановить исходное назначение и проверить сообщения, не переносить вслепую.

## Журнал и ручное восстановление

`/admin/reception` находится в «Люди → Заявки», страницы по 50 анкет.
Сервер проверяет права и для чтения, и для POST `/api/admin/reception`.
Действия имеют версию delivery для защиты от устаревших форм и записываются
в `events` как `reception.delivery_review` внутри той же транзакции.
Payload содержит ссылки/ревизию/действие и отметку ручной сверки, без анкеты/секретов.

«Проверить доставку» открывает ID заявителя, chat/topic/message, время/ревизию
попытки и её счётчик. Это данные для ручного поиска, не автоматическое доказательство.
В needs_review доступны:

1. «Подтвердить доставку»: сверить **ревизию попытки** с сообщением в теме,
   указать message ID и отдельное подтверждение. При известном ID менять его нельзя.
   Если в Core уже новая ревизия, worker затем обновит существующее сообщение.
2. «Разрешить повтор»: явно подтвердить отсутствие публикации или неприменённые
   правки известного сообщения. Без этого POST отклоняется. Не использовать это
   действие просто из-за таймаута. Если результат всё ещё неизвестен — оставить needs_review.

Ответы форума на подтверждённые публикации разрешаются через новый lookup
delivery → Telegram ID и затем идут существующим relay. Старые relay mappings
проверяются первыми. Webhook, исходящая личная переписка и Dev auth не изменены.
Этап 4 [согласует приглашения](reception-invitations.md) с решением Хранителя.

## Проверка в настоящем Telegram перед включением

Не включать production флаги на основании одного build. Сначала применить миграцию
на staging и проверить worker с обоими флагами выключенными. Использовать отдельный
тестовый bot/forum/topic, HTTPS Mini App и учётные записи кандидата/Хранителя.
Убедиться, что Reception bot может отправлять/редактировать сообщения в теме,
а privacy mode/права получения ответов соответствуют действующей настройке relay.
Не менять production webhook для эксперимента.

Проверить одну отправку, повтор неизменённой формы, изменение данных и отзыв возраста
в том же message ID, ответ из форума в личный чат и прежнюю обычную переписку.
Затем контролируемо оборвать ответ после возможной отправки: должна быть needs_review,
без дубля после перезапуска и второго worker. Сверить вручную обе ветки восстановления,
права непривилегированного пользователя, журнал событий и задержку 429.
Проверить Android/iOS/Desktop Mini App: pending, delivered, needs_review и ожидание правок.
Отключить тестовый флаг, осмотреть оставшиеся pending/needs_review и только после
отдельного разрешения планировать deploy/включение в production.

PostgreSQL tests используют изолированный `RECEPTION_TEST_DATABASE_URL`
(`127.0.0.1`, БД `reception_tests`), случайные схемы и отдельные тестовые Telegram ID.
При параллельном применении миграций предварительно создать pgcrypto в public,
чтобы тестовые схемы не соревновались за глобальное расширение.

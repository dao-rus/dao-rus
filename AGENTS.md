# Правила работы в репозитории

## Начало нового чата

Перед первой задачей восстановить контекст проекта: прочитать этот файл, корневой
`README.md`, `docs/architecture/current-state.md`, затем только относящиеся к задаче
документы и существующую реализацию. Читать документацию после проверки, что checkout
соответствует актуальному состоянию удалённой ветки или явно известно, почему он от неё
отличается. В том же чате не перечитывать всё заново; догружать контекст при переходе в
другую область проекта.

## Актуальность checkout перед архитектурной работой

Перед задачей, которая меняет схему БД, доменную модель, auth, permissions, безопасность
или другой системный контракт:

1. проверить текущий branch, `HEAD`, `origin/main` и состояние рабочего дерева;
2. обновить refs;
3. убедиться, что канонические документы, указанные в задаче, существуют в актуальном
   `origin/main`;
4. если checkout отстаёт и рабочее дерево чистое — безопасно синхронизировать его
   fast-forward;
5. если есть локальные изменения, divergence или иной риск потерять работу — не делать
   merge/rebase/reset автоматически; остановиться и сообщить состояние;
6. только после этого читать канонические документы и начинать реализацию.

Не начинать системное изменение, если указанный источник истины отсутствует в текущем
checkout или его актуальность не подтверждена.

## Общие правила

- Выполнять минимально достаточное изменение в пределах запроса. Сначала искать
  существующую сущность или механику и предпочитать её расширение созданию
  параллельного решения.
- Не предполагать то, что можно проверить в коде, документации, конфигурации или
  состоянии среды. Проверенные факты явно отличать от предположений.
- Не проводить сопутствующий рефакторинг и не менять соседнее поведение без
  необходимости.
- Архитектурные решения сверять с моральным кодексом ДАО Русь, народовластием,
  самостоятельностью участника и минимизацией централизованного доверия. Не
  превращать DAO Core в обычный вертикально управляемый сервис ради локального
  удобства реализации.
- Доменную механику DAO Core держать независимой от конкретного интерфейса и
  канала. Web UI, Telegram-бот, Telegram Mini App, AI-агент и возможный будущий
  собственный мессенджер должны быть адаптерами к одному ядру. Telegram-first —
  текущая тактика интеграции, а не фундаментальная зависимость. Telegram-
  специфичную логику оставлять в адаптерах и ingestion-слое; канонические
  сущности, правила и состояние ДАО не должны зависеть от Telegram без
  предметной необходимости.
- Если выбор существенно влияет на модель данных, безопасность, управление или
  UX и не следует однозначно из уже принятых решений, кратко сообщить варианты и
  запросить решение пользователя. Несущественную неопределённость разрешать
  простейшим согласованным способом.
- При препятствии сначала установить причину. После первой подтверждённой ошибки
  доступа, credentials, network или deployment не перебирать нештатные обходы, а
  сообщить, что заблокировано и какое минимальное действие нужно для продолжения.
- `interfaceTextFields` (`apps/core/src/lib/interface-texts.ts`) — единственный реестр
  редактируемых пользовательских текстов оболочки. Новый ключ добавлять туда,
  чтобы он автоматически появлялся в `/admin/interface`; миграция БД для нового
  ключа не нужна. Не оставлять такую копию отдельным hardcoded literal без причины;
  технические ошибки, security/auth сообщения, aria-label, служебные статусы и
  динамические данные в этот реестр не включать.
- Канонический текст Кодекса хранится в `docs/governance/code.md`. Код интерфейса
  может содержать только синхронизированную runtime-проекцию этого текста; комментарии,
  оценки и практика применения не должны незаметно изменять канон.
- Устойчивое новое архитектурное правило, процедуру или повторяющуюся ловушку
  фиксировать в подходящей документации. Не превращать документацию в журнал
  выполненных действий.

## Проверки по уровню риска

Выбирать минимальный набор проверок, достаточный для уверенности в результате.
Полный test suite не является автоматическим финальным шагом каждой задачи.

### 1. Малое изменение

Примеры: документация, текст интерфейса, подпись, локальный стиль без изменения
логики или контракта.

- проверить diff и `git diff --check`;
- проверить изменённую страницу или фрагмент интерфейса, если это доступно;
- запускать typecheck или узкую синтаксическую проверку, только если менялась
  разметка либо исполняемый код, а не один строковый литерал;
- не запускать `npm test` и полный build без дополнительной причины.

### 2. Обычное изменение

Примеры: локальная функция, компонент, route handler или поведение одной
подсистемы.

- выполнить typecheck для TypeScript-изменений;
- запустить ближайшие релевантные тестовые файлы через `npm test -- <path>`;
- выполнить узкую runtime/smoke-проверку изменённого поведения;
- не запускать несвязанные тесты всего проекта, если область влияния ограничена.

### 3. Системное изменение

Примеры: схема или миграция БД, auth, безопасность, deployment, общий контракт,
разделяемая инфраструктура либо широкий рефакторинг.

- выполнить полный `npm test` в `apps/core`;
- выполнить `npm run typecheck` и, когда затронуты сборка или runtime,
  `npm run build`;
- проверить целостность данных, миграции и фактический runtime на уровне,
  соответствующем изменению.

Повышать уровень проверки нужно из-за реального радиуса влияния, явного требования
пользователя или правил конкретной подсистемы, а не просто потому, что более
широкая команда существует. Если узкой проверки нет, выбрать ближайшую
экономичную проверку и кратко указать это в отчёте.

## Commit, push и production deploy

- **Production deploy — обычный финал задачи, а не отдельный последующий этап.**
  Если изменение меняет production runtime, прошло требуемые проверки и безопасный
  порядок развёртывания понятен, после выполнения самостоятельно доводить его до
  рабочего состояния: commit → fast-forward merge в `main` → push `main` →
  production deploy штатным `apps/core/deploy/update.sh`.
- Не добавлять в промпт запрет вида «production не разворачивай» просто из
  осторожности. Откладывать deploy только для действительно сложных или рискованных
  случаев: неясная миграция данных, auth/permissions, secrets, deployment-
  инфраструктура, потенциально разрушительная операция, широкий радиус влияния,
  незавершённый зависимый этап либо явное указание пользователя.
- Для production DAO Core использовать SSH host `dao-rus-prod`; парольную
  авторизацию не использовать. Штатный deploy запускать через этот host.
- После deploy проверить состояние контейнеров и минимальный HTTP/runtime smoke
  изменённого пользовательского пути. Не считать один успешный push завершением
  задачи, если пользователь ожидает изменение на работающем сайте.
- Deploy не нужен для изменений, которые не меняют production runtime
  (например, только документация или тесты).
- Перед изменениями схемы/миграциями БД, auth/permissions, secrets, deployment-
  инфраструктуры, потенциально разрушительными операциями с данными или иным
  изменением с существенным радиусом риска остановиться и запросить решение
  пользователя, если безопасный порядок действий не следует однозначно из уже
  принятого плана.
- Если deploy заблокирован неизвестной ошибкой, доступом, credentials или
  состоянием среды, после установления причины не перебирать обходы: сообщить
  проблему и минимальное действие, необходимое для продолжения.

## Завершение задачи

Кратко сообщить: что изменено, какие файлы затронуты, что фактически проверено,
были ли commit/push/deploy и какие ограничения остались. Не заявлять о действии
или проверке, которые не выполнялись.
